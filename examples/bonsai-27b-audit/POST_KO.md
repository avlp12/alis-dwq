# Bonsai 27B 감사기(監査記): "ternary"와 "1-bit"는 실측으로 뭐가 나오나

*PrismML 자료로 명시 표기한 것을 제외한 아래 모든 수치는 M3 Ultra(512GB) 한
대에서 공개 도구([alis-dwq](https://github.com/avlp12/alis-dwq))로 직접
측정했다 — stock mlx-lm 0.31.3 기준이되, 1-bit 팩의 런타임 행들만 PrismML의
MLX fork가 필요했다(해당 섹션에 명시). 원시 측정 로그와 감사 스크립트는 리포에 게시돼 있고
([examples/bonsai-27b-audit](https://github.com/avlp12/alis-dwq/tree/main/examples/bonsai-27b-audit)의
`logs/` + `audit_1bit.py`), 두 가중치 세트 모두 공개다(Bonsai: Apache-2.0,
원본: Qwen/Qwen3.6-27B) — 커맨드는 글 끝에.*

PrismML의 [Ternary Bonsai 27B](https://huggingface.co/prism-ml/Ternary-Bonsai-27B-mlx-2bit)는
Qwen3.6-27B의 1.71 bits/weight ternary 표현을 내걸고 — 감사한 MLX 산출물은
그 코드를 2-bit affine 슬롯에 저장하며 8.49GB다 — 15개 thinking-mode 벤치마크
평균으로 "FP16 품질의 ~95% 유지"를 주장한다. 방법론은 비공개지만 입력과
출력은 공개다. 그래서 팩과 FP16 원본을 받아 직접 쟀다: 토큰 레벨 발산, 언어
슬라이스별 손상, 두 가지 디코딩 영역에서의 퇴화 프로브, KV 캐시 내성, 그리고
변환 자체에 대한 가중치 포렌식.

한 줄 결론: **포맷 주장은 정직하고, 헤드라인 품질 주장은 벤치마크가 재는 축
위에서만 참이며, 그 축을 벗어나면 벤치마크 평균이 구조적으로 볼 수 없는
방식으로 망가진다.**

프레이밍 주석을 앞에 둔다. 유지율(94.6%/89.5%), 15-벤치 표, tok/s·배터리
수치는 전부 PrismML 제공이며 EvalScope + vLLM을 H100에서 돌린 — 그들의 CUDA
경로, 샘플링, judge-스코어 — 측정이다. 아래 내용은 그 수치를 그 자체의
조건에서 반박하지 않는다. 이 감사가 보태는 것은 그 방법론이 구조적으로 잴 수
없는 것들이다. 범위: **ternary 팩**은 stock mlx-lm에서, **1-bit 팩**은 PrismML의 MLX
fork를 격리 venv에 빌드해서 — 두 팩 모두 아래의 전체 런타임 배터리를 거쳤다.

## 사실로 확인된 것들

공정하게, 크레딧부터. 세 가지 주장이 적대적 측정을 통과했다:

- **확인 가능한 범위에서 ternary 라벨은 진실이다.** affine 언어 텐서 498개
  전수의 코드 히스토그램을 복원한 결과(`mx.dequantize` 경유, 패킹 가정 없음):
  전부 정확히 3레벨만 쓴다 — 2-bit 컨테이너의 4번째 레벨을 쓰는 가중치는
  *0개*다. 레벨 사용은 거의 균일(35.2%/29.7%/35.1%)해서 실효 페이로드는
  명목 2.00 중 1.58 b/w — log₂3 상한의 99.7%다(텐서별 엔트로피 min 1.551 /
  중앙값 1.581 / max 1.585). 4-bit HQQ 비전 타워는 이 스캔 범위 밖이다(카드에
  공시된 사항). 이 팩을 만든 것이 무엇이든, 정보이론이 허용하는 한계까지
  알파벳을 쥐어짜고 있다.
- **stock mlx-lm에서 로드·생성이 된다.** 커스텀 커널은 속도 경로일 뿐 포맷
  요구사항이 아니다(ternary 팩 한정 — 1-bit는 아니다).
- **4-bit KV 캐시 내성 주장은 재현된다.** KV 캐시를 4-bit로 양자화했을 때
  자기 자신의 FP16-KV 실행 대비 유발되는 self-KL: ternary 빌드가 FP16 대비
  슬라이스에 따라 **9–145× 낮다**(EN 15×, code 145×, ZH 9.4×; 화이트페이퍼
  주장은 12–95×). 독립 하네스에서 재현된 실재 현상이다 — 단서는 아래에서.

## 벤치마크가 보여주지 않는 것들

**FP16과의 토큰 레벨 발산은 크고, 고르게 분포하지 않는다.** 고정된 3,072토큰
슬라이스(⅓ 영어 wikitext, ⅓ 코드, ⅓ 중국어)에서:

| 슬라이스 | KL(FP16‖Bonsai) | top-1 flip |
|---|---|---|
| EN | 0.58 | 21.0% |
| code | 1.32 | 22.8% |
| ZH | 1.32 | **45.6%** |
| 전체 | 1.08 | 29.8% |

중국어 토큰의 절반 가까이가 argmax부터 바뀐다. 언어별 분리 결과를 보고하지
않는 집계형 벤치마크 스위트에서는 이 격차가 드러나지 않는다.

**동일 하네스 퍼플렉시티 트라이앵글.** 512토큰 비중첩 윈도, 동일 스코어러
(`llama-perplexity` 청크 스코어링의 검증된 미러), 동일 코퍼스 바이트, 동일
베이스 모델:

| 빌드 | 크기 | wikitext | code | ZH |
|---|---|---|---|---|
| FP16 Qwen3.6-27B | 54 GB | 6.34 | 2.22 | 8.78 |
| Bonsai ternary (훈련됨) | **8.5 GB** | 11.31 | **2.82** | **26.85** |
| Bonsai 1-bit (훈련됨; 그들의 fork에서) | **4.1 GB** | 12.19 | 3.14 | **41.81** |
| naive 혼합 PTQ, 무학습 (FFN 2-bit) | 14 GB | 11.19 | 3.23 | 17.12 |
| + anchor-guard 클립 서치, 무학습 | 14 GB | **9.91** | 3.04 | 15.80 |

크기가 다르고(8.5 vs 14 GB) 방법도 통제되지 않았으므로 훈련 효과를 분리하는
표가 아니다 — 레시피-대-레시피로 읽어야 한다. 이 표가 확립하는 것:
**code**에서 Bonsai 엔드포인트는 FP16의 1.27×에 도달해 더 큰 무학습 베이스라인
둘을 모두 이긴다. **중국어**에서는 **FP16의 3.06× — 아무것도 훈련하지 않은
naive min-max PTQ(1.95×)보다 나쁘다.** 이 변환이 무엇을 최적화했든, 비영어
질량이 그 값을 치렀다. (저비트 손상이 비영어 슬라이스에 집중되는 걸 실측한
게 이걸로 세 번째 모델 패밀리다. 내 레시피들이 타깃 언어 45% 믹스로
캘리브레이션하는 이유다.)

**벤치 점수가 숨기는 디코딩-영역 손상.** 64토큰 raw-text 프롬프트에서 greedy로
256토큰을 이어 쓰게 하면:

| | EN | code | ZH |
|---|---|---|---|
| FP16 distinct-4gram / 사이클 | 0.632 / 없음 | 0.941 / 없음 | 0.996 / 없음 |
| Bonsai distinct-4gram / 사이클 | **0.134 / 주기13** | **0.411 / 주기2** | **0.079 / 주기18** |

ternary 빌드는 세 슬라이스 모두 짧은 반복 사이클에 갇히고, FP16 대조군은 같은
프로브에서 전부 깨끗하다. 슬라이스당 프롬프트 1개이므로 이 프로브 하에서의
엔드포인트 차이로 읽어야 한다 — 차이 나는 것은 변환 번들(양자화 + 팩을 만든
리튠 일체)이고, 그 성분들은 여기서 분리되지 않는다. PrismML 스스로 발표한
관찰(관행적 IQ2_XXS 빌드가 MMLU-Redux 88.93을 지키면서 AIME26에서 57.5로
추락)과 같은 패턴이다: sub-4-bit 손상은 장기 호흡 행동에 집중되고, 단문
벤치는 거기를 보지 않는다.

**그리고 PrismML이 정당하게 요구할 대조 실험을 직접 돌렸다** — 같은 프로브를
그들이 문서화한 샘플링 파라미터(generation_config: T=1.0, top-k 20, top-p
0.95; 슬라이스당 시드 5샘플, 같은 raw-text 프롬프트)로. 결과: **하드 사이클은
사라진다 — 두 모델 모두 15/15 샘플 사이클 없음.** greedy 결과는 유효하되
반드시 이 한정사와 함께 인용해야 한다: 이 퇴화는 이 프로브의 greedy 디코딩에
특정된 현상이고, 챗 템플릿 경유 동작과 준-greedy 설정은 미측정이다. 온도에서의
distinct-4gram 전모(슬라이스별 평균 / 5샘플 중 최저):

| | EN | code | ZH |
|---|---|---|---|
| Bonsai 평균 / 최저 | 0.723 / **0.265** | **0.841** / 0.589 | 0.952 / 0.913 |
| FP16 평균 / 최저 | 0.840 / 0.660 | 0.808 / 0.672 | 0.978 / 0.964 |

정직한 독법: Bonsai의 최저 샘플은 EN에서 훨씬 낮게 떨어지지만, code의
*평균*은 오히려 FP16을 이긴다 — 서빙 온도에서 이것은 두 슬라이스의 더 무거운
저다양성 꼬리이지 붕괴가 아니며, 모델당 n=15라 방향성 지표다. 실무적 결론:
greedy로 디코딩하는 워크로드(다수의 수학/코드 하네스, constrained decoding,
일부 에이전트 스택)는 이 프로브를 직접 돌려봐야 하고, 샘플링 챗은 상당히
안전해 보인다.

## 이 변환의 정체 (가중치 포렌식)

양 끝점이 공개라 방법의 *클래스*를 좁힐 수 있다. MLP 40개 + attention 36개
텐서, 각 4가지 지문(스펙트럼은 실행당 8개 샘플 텐서):

- **직접 해석적 라운딩이 아니다.** 코드가 원본 가중치의 최적 임계값 사영과
  MLP 14.9% / attention 11.7% 불일치 — 가중치 자체가 움직였다.
- **기저 회전은 없었다**(샘플 텐서 스펙트럼 상관 0.993/0.985, 원소별 상관도
  높음).
- **스케일은 absmean 계열이다**(MLP 스케일 비율 ≈0.83, 텐서 간 편차 작음;
  attention은 0.78–1.01 스팬). BitNet식 해석적 스케일과 일치 — *그 자체로는*
  훈련의 증거가 아니다.
- **집계 수준의 저장-순서 보상 지문은 없다**(드리프트 −0.001/−0.003; 개별
  attention 텐서는 ±0.04까지) — 그러나 act-order 변형은 열을 뒤섞인 순서로
  처리해 이 검사에 보이지 않는다. 따라서 정직한 판정 경계는: **QAT/증류형
  변환 또는 순서-치환 보상 PTQ(act-order GPTQ 클래스). 엔드포인트만으로는 이
  둘을 분리할 수 없다.** 창업진의 계보(Optimal Brain Surgeon)를 감안하면 보상
  계열은 기각된 가설이 아니라 살아있는 가설이다.

(이 분석의 초기 판정은 "훈련이다, GPTQ 기각"이었다 — 적대적 리뷰가 act-order
GPTQ가 정확히 여기서 측정된 평탄한 집계 드리프트를 만든다는 걸 시뮬레이션으로
보여 그 추론을 깼다. 위의 한정 판정이 *가중치*가 지지하는 범위다.)

**그래서 판별 실험을 직접 돌렸다.** 변환이 노이즈-주입/QAT형 훈련이라면 활성
분포가 *평탄화*돼 있어야 하고, 출력 보존형 보상 PTQ라면 FP16과 같아야 한다.
모든 디코더 블록 출력의 레이어별 초과 첨도, 고정된 혼합 배치 하나, 무학습
PTQ 빌드를 대조군으로:

| | 초과 첨도 중앙값 |
|---|---|
| FP16 Qwen3.6-27B | 2372 |
| 무학습 PTQ 대조군 (clip, FFN 2-bit) | **2353 — FP16 수준 그대로** |
| Bonsai ternary | **94.6 — ~25× 평탄, 64/64 레이어 전부** |

하중을 받치는 건 대조군 행이다: 저비트 가중치 자체는 활성 기하를 건드리지
않으므로, 평탄화는 Bonsai *변환*의 속성이다 — 그리고 전 레이어에 걸친 계통적
25× 첨도 붕괴는 (출력을 보존하는) 보상의 목적함수와 정반대이면서, 노이즈-강건
훈련의 예측 지문 그 자체다. 아래 KV 내성의 메커니즘도 이것이 공급한다.
가중치-단독 판정은 위에 적은 대로 한정된 채 두되, **활성 증거까지 합치면
저울은 QAT/증류 분기로 기운다.**

수렴 하나를 기록해 둘 가치가 있다: PrismML이 공개적으로 설명하는 포맷 —
`w = s_g · t_i`, 가중치 128개 그룹마다 공유 FP16 스케일 1개 — 은 지문이
복원한 것과 정확히 같다. 비공개로 남은 것의 핵심은 `t_i`의 선택 방법이다:
어떤 해석적 사영으로도 설명되지 않는, 움직인 코드들.

## 1-bit 팩: 정직한 이진, 유사한 지문, fork 전용 런타임

~4GB짜리 "1-bit" 팩이 더 급진적인 산출물인데, **stock mlx에서는 실행되지
않는다** — mlx 0.31.2에 `bits: 1` 커널이 없다(`quantize` 거부, `dequantize`
커널 조회 실패). PrismML의 MLX fork가 문서화된 런타임 경로다. 코드를 수동
언팩해(스크립트+전체 출력은 리포에; 비트 순서는 ternary 팩에서
`mx.dequantize` 코드와 교차 검증) 깊이·모듈 유형에 걸쳐 6개 텐서를 샘플링:

- **샘플 범위에서 진성 대칭 이진**: 그룹별 레벨이 정확히 {−s, +s}, 부호 균형
  49.9%, 그룹별 코드 엔트로피 0.994/1.0 — PrismML이 설명하는 포맷과 일치.
  컨테이너 디테일: 광고되는 **1.125 bpw**는 그룹당 FP16 스케일 하나만 센
  숫자다. MLX affine 컨테이너는 그룹당 *bias*까지 실어 실제 저장은
  **1.25 bpw**다(디스크의 4.1GB는 1.125가 아니라 이 숫자와 맞아떨어진다).
- **같은 "가중치 이동" 서명**: 코드가 sign(원본)과 88.3% 일치 — **부호의
  11.7%가 원본에서 이탈**했다. ternary 팩의 움직인 코드의 이진 판이다.
  (이 6-텐서 샘플에서 최저 일치는 `linear_attn.in_proj_a` 83.6%였지만,
  ternary 팩의 attention 스윕에서는 최저 패밀리가 *다른* `in_proj_b`
  58.9%였다 — "같은 텐서가 제일 많이 움직였다"는 교차-팩 주장은 성립하지
  않는다.)
- **스케일은 해석적 최적치 근방**(중앙값 비율 1.01 vs 그룹별 MSE-최적
  반폭 — 2레벨에선 그것이 곧 absmean 규칙). 가중치-이동 최적화 아래의 해석적
  absmean 스케일과 일치하는 결과이되, 6개 텐서로 증명이라 할 수는 없다.

그리고 fork를 빌드해(격리 venv; 빌드에 이빨이 있다 — cmake가 venv 파이썬을
핀하지 않으면 시스템 최신 파이썬을 집어가고, 기본 빌드 격리에서는 휠에
`libmlx.dylib`이 빠진다) 1-bit 팩에도 전체 런타임 배터리를 돌렸다:

- **KL vs FP16: 전체 1.351, flip 33.6% — 중국어는 토큰의 과반(50.9%)이
  뒤집히고** 윈도 퍼플렉시티는 FP16의 4.76×(41.8 vs 8.78)에 이른다. 한편
  wikitext는 1.92×를 지키고 code(3.14)는 *~4배의 바이트를 쓰는 무학습 PTQ
  베이스라인을 여전히 이긴다* — 변환의 EN/code 경쟁력과 비영어 비용이 둘 다
  공격성에 비례해 커진다.
- **온도 방어선이 뚫리기 시작한다.** ternary 팩은 서빙 온도에서 15/15
  사이클 없음이었는데, 1-bit 팩은 15개 중 1개가 루프했다(EN, 주기 21).
  ternary를 보호하던 "greedy에서만 루프한다"는 한정사가 한 비트 아래에서는
  얇아진다.
- **KV 면역은 비트가 내려갈수록 강해진다: FP16 대비 82×**(self-KL 0.00198;
  ternary는 56×). 첨도 메커니즘이 예측하는 용량 추세가 이제 두 점으로
  그려진다: 더 공격적인 변환 → 더 평탄한 활성 → 더 강한 캐시 강건성, 그
  대가는 출력 날카로움과 퇴화.

## KV 내성은 따로 한 단락을 받을 자격이 있다

KV 이야기는 그들의 폰 피치에서 하중을 받치는 기둥이다: 그들의 런칭 자료
기준, 262K 풀 컨텍스트에서 FP16 캐시는 ~17.2GB — 모델보다 크다 — 이고 이를
~4.3GB로 끌어내리는 것이 4-bit KV다(64층 중 16층만 캐시하는 하이브리드 백본
위에서). 그래서 이 내성 주장이 *재현된다*는 사실이 중요하다(슬라이스별
9–145×, 모델당 동일한 16개 양자화 가능 캐시 기준). 그리고 위의 첨도 측정으로
이 내성은 이제 메커니즘을 갖췄다: **FP16보다 ~25× 평탄한 활성**은 캐시 양자화
노이즈를 비례적으로 무해하게 만든다 — 면역은 추측이 아니라 측정된, 변환의
속성이다(무학습 PTQ 대조군은 FP16 수준 첨도를 유지하고, 같은 세션에서 다른
모델 패밀리의 PTQ+DWQ 빌드들도 이 급의 면역 근처에 못 갔다). 같은 메커니즘의
뒷면: 평탄화·재성형된 내부 분포가 뾰족해진 출력의 greedy-루프 행동과
공존한다 — 강건성과 퇴화는 하나의 훈련 선택이 가진 두 얼굴로 보인다.
장기-호흡 손상 없이 강건성만 유도할 수 있는가(예: 증류 리튠 중 KV-양자화
노이즈 주입)는 열린 실험이고, 아마 이 릴리스가 가리키는 가장 유용한 연구
방향이다.

## 정리

1. **포맷 주장은 정직하다 — 감사 도구로 몇 분이면 확인된다.** 스캔한 모든
   언어 텐서에서 진성 ternary, 1-bit 샘플에서 진성 대칭 이진, 정보-상한급
   코드 사용, 숨겨진 정밀도 없음.
2. **"FP16의 95%"는 벤치마크 모양의 숫자다.** 토큰 레벨로는 argmax의 30%가
   움직이고, 중국어는 46%가 뒤집히며, 윈도 PPL은 여기서 잰 무학습 PTQ
   베이스라인 아래다(크기/방법 비매칭이지만 — 그 베이스라인은 *아무것도*
   훈련하지 않았다). 저비트 헤드라인을 믿기 전에 평가를 언어별로 썰어라.
3. **단문 지표는 디코딩-영역 손상을 숨긴다** — greedy에서는 하드 루프(FP16
   대조군은 클린), 그들이 문서화한 샘플링 파라미터에서는 사이클 없음. 당신의
   워크로드가 greedy로 돈다면 — 다수의 수학/코드 하네스가 그렇다 — 이 구분이
   전부다. 퇴화 프로브를 두 영역 모두에서 돌려라.
4. **"라벨은 비트폭이 아니다"는 양날의 칼이다.** PrismML의 런칭 스레드는 혼합
   정밀도 라벨을 정당하게 때린다(그들의 계산: Q4_K_XL ≈ 5.2 b/w, IQ2_XXS ≈
   2.8) — 그리고 그들의 *코드*는 광고 그대로다. 그런데 같은 렌즈를 그들의
   산출물에 대보라: "1.71 b/w → 5.9GB"와 "1.125 b/w → 3.9GB"는 이상적 표현의
   숫자다. 출하된 MLX ternary 팩은 3레벨을 2-bit 슬롯에 담아 **8.49GB**이고,
   출하된 MLX 1-bit 팩은 그룹당 bias 포함 **1.25 b/w**를 저장하며 그들의
   fork에서만 돈다. 광고된 숫자는 표현을 기술할 뿐, 배포 가능한 산출물이
   아니다. 어디서 많이 듣던 얘기 아닌가?
5. **KV 내성은 실재하고, 이제 측정된 메커니즘이 있다**(일반 PTQ는 만들지
   않는 25× 평탄화된 활성). greedy-영역 손상 없이 그것을 제조할 수 있는가가
   훔칠 가치가 있는 열린 질문이다 — ternary 자체가 아니라 그것이 내가 쫓을
   것이다.

## 재현

```bash
git clone https://github.com/avlp12/alis-dwq && cd alis-dwq
python3 -m pip install "mlx-lm>=0.31"

# 포맷 감사 (몇 분, 학생 팩만 필요)
python3 -m alis_dwq.code_entropy --model <bonsai-pack> --save entropy.npz

# 토큰 레벨 KL + greedy 퇴화 + KV 프로브 (양 엔드포인트)
python3 -m alis_dwq.eval_kld --model <qwen36-fp16> --save-ref ref.npz \
  --loop-probe 256 --kv-probe 4
python3 -m alis_dwq.eval_kld --model <bonsai-pack> --ref ref.npz \
  --loop-probe 256 --kv-probe 4

# 온도-매칭 대조 (양 엔드포인트)
python3 -m alis_dwq.eval_kld --model <qwen36-fp16> --save-ref /tmp/x.npz \
  --loop-probe 256 --loop-temp 1.0 --loop-top-k 20 --loop-top-p 0.95 --loop-samples 5
python3 -m alis_dwq.eval_kld --model <bonsai-pack> --save-ref /tmp/y.npz \
  --loop-probe 256 --loop-temp 1.0 --loop-top-k 20 --loop-top-p 0.95 --loop-samples 5

# 512-윈도 PPL (llama.cpp-매칭 스코어러)
python3 -m alis_dwq.ppl_windows --model <any-build> --window 512 \
  --text data/wikitext.txt data/code.txt data/zh.txt

# 방법 포렌식 (두 가중치 세트 필요)
python3 -m alis_dwq.weight_forensics --original <qwen36-mlx-bf16> \
  --transformed <bonsai-pack> --pattern mlp --max-tensors 40
python3 -m alis_dwq.weight_forensics --original <qwen36-mlx-bf16> \
  --transformed <bonsai-pack> --pattern "linear_attn|self_attn" --max-tensors 36

# 1-bit 팩 포맷 감사 (fork 불필요)
python3 examples/bonsai-27b-audit/audit_1bit.py

# 활성 첨도 판별자 (스크립트 상단의 모델 경로 수정)
python3 examples/bonsai-27b-audit/kurtosis_probe.py
```

전체 원시 로그, 텐서별 지문, 감사 프로토콜:
[examples/bonsai-27b-audit](https://github.com/avlp12/alis-dwq/tree/main/examples/bonsai-27b-audit).
