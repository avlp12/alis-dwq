# alis-dwq

**DWQ for very large MLX models on Apple Silicon** — layerwise rounds + two-phase targets, so quantized models that are *hundreds of GB* can be distillation-tuned on a single Mac (or a pair) without OOM.

Built and battle-tested on a 512 GB M3 Ultra pair while shipping public quants of GLM-5.2 (745B MoE) and Hy3 (295B MoE).

## Why

`mlx_lm dwq` fine-tunes the quantization `scales`/`biases` of a quantized model ("student") against a higher-precision teacher's logits. It works great — until the student is large:

1. **The teacher may not fit next to the student.** Two-phase fixes this: dump the teacher's top-k logits to disk once (teacher alone in memory), then train the student against the dump (student alone in memory — with targets on disk, mlx-lm never loads the teacher for training).
2. **The student's own backward may not fit at all.** Training *every* layer's scales in one step materializes large per-layer intermediates for the quantized-matmul VJP simultaneously. A 242 GB / 745B-parameter MoE student dies in the first step on a 512 GB machine — at sequence length 1024, 512 *and* 256, with `--grad-checkpoint`, at batch size 1. Distributing doesn't rescue it (`Send` has no VJP in the pipeline path).

**Layerwise rounds** fix (2): train at most K layers per round. Since `value_and_grad` only differentiates unfrozen parameters, backward memory is bounded by K instead of by the model. Rounds run deepest-first (best-conditioned gradients — shallow-first diverged in our runs), and every round is validated and rolled back if it didn't improve, so the procedure is monotone by construction.

Measured on the 745B case: **OOM at step 0 → stable training at ≈334 GB peak** with K=8.

## Install / use

Works on **stock mlx-lm ≥ 0.31** (the layerwise trainer ships here as a patch module; upstream PR [ml-explore/mlx-lm#1499](https://github.com/ml-explore/mlx-lm/pull/1499) adds `--layers-per-round` natively — once merged you can use either path).

For a current large-MoE example with mixed full/sliding caches, strict router
exclusions, precomputed-target verification, and separate compact and
quality-first release arms, see the
[Laguna S 2.1 recipe](examples/laguna-s-2.1/README.md).

```bash
git clone https://github.com/avlp12/alis-dwq && cd alis-dwq
pip install mlx-lm  # >= 0.31
```

### 0. Measure expert traffic first (optional — sizes the recipe)

Expert-hybrid quants (e.g. [NVFP4 top-64 + NF3 tail on GLM-5.2](https://huggingface.co/madeby561/GLM-5.2-MXFP8-NVFP4-NF3-Hybrid)) work because routing traffic is heavily skewed. Measure that skew for your model before picking per-layer bits:

```bash
python -m alis_dwq.expert_traffic --model <model> --save traffic.npz --top 64
python -m alis_dwq.expert_traffic --load traffic.npz --top 32   # re-analyze, no model load
```

Hooks `SwitchGLU`/`SwitchMLP` (architecture-agnostic), runs the same fixed EN/code/ZH slices as `eval_kld`, and reports per layer: top-N traffic share, experts needed for 90%/99% of mass, dead experts, JSD(EN, ZH), and the worst per-slice overlap of the top-N set. Uses for the numbers:

- **top-N share high everywhere** → a salient/tail bit split is on the table; **low or uneven** → spend bits per-layer instead.
- **low min-overlap / high JSD layers** → the salient set is language-dependent there; a static salient set chosen on EN traffic under-serves ZH (the per-expert version of the ZH damage the 45% mix corrects). Give those layers more bits, and make sure the calibration mix covers the language whose experts differ.
- **dead experts** on the calibration slice get no DWQ gradient — if a layer has many, widen the mix before trusting a low-bit build of it.

Measured reference point (GLM-5.2 745B, EN/code/ZH mix, 2026-07-12): routing is **flat** — top-64/256 experts carry only 39–57% of frequency (45–72% of `--norms` mass), n90≈170–207 of 256, dead≈0, busy-but-weak = 0. Salient/tail bit-splits and REAP-style pruning are contraindicated on this family; and JSD(EN,ZH) reaches 0.4 mid-stack with 44–61% min-overlap — the language-dependent-experts effect the 45%-ZH calibration mix exists to cover.

Independently confirmed by the [NF3-hybrid's v3.6 update](https://huggingface.co/madeby561/GLM-5.2-MXFP8-NVFP4-NF3-Hybrid) (2026-07-09): swapping its top-64 selection from routing frequency to **measured per-expert quantization damage** cut KLD 16% and gained +0.5 GPQA on this same model. The *frequency criterion* was wrong, not expert-level differentiation itself — our student-only damage proxy is `code_entropy --per-expert` (§1a).

Add `--norms` (experimental) to also accumulate each selected expert's output L2 norm — a [REAP](https://arxiv.org/abs/2510.13999)-saliency proxy (their criterion is `gate × ‖out‖`; the gate factor is applied outside `SwitchGLU` and isn't captured). The report then flags **busy-but-weak** experts (selected often, contributing little): REAP's prune candidates, or bit-cut candidates for a hybrid recipe.

### 1. Build a calibration mix (optional but recommended)

`dwq_data/train.jsonl` + `valid.jsonl`, one `{"text": ...}` per line. A
`manifest.json` is strongly recommended; when present, its exact bytes and any
declared `tokenizer_files_sha256` are enforced. Without one, the launcher binds
a derived manifest made from the two JSONL hashes. Language mix matters: low-bit
damage concentrates in the model's non-English mass (we measured ZH slices
1.4–3.9× worse than EN on two different MoE families); a ≈45% target-language
mix is what recovered it. Without `ALIS_DWQ_DATA_DIR`, mlx-lm's default
`--data-path` loader is used and release-grade target contracts are unavailable.

Raw `{"text": ...}` rows use mlx-lm's normal `TextDataset` processing. If every
row already contains the exact chat-template output, set
`ALIS_DWQ_TEXT_TOKENIZATION=preformatted_chat`; this uses
`add_special_tokens=False`, appends no EOS, and hashes the final truncated token
IDs. Use the same mode for target creation and training. Contracted local runs
require a positive seed.

Two hygiene rules from [Unsloth Dynamic 2.0](https://unsloth.ai/docs/basics/unsloth-dynamic-2.0-ggufs)'s methodology notes: **(a) keep calibration and evaluation corpora disjoint** — calibrating on wikitext-like data while gating ships on wikitext PPL overfits the quant to the gate (our held-out gates are wikitext-heavy; check the mix before trusting a small win); **(b) instruct/thinking models should be calibrated through their chat template** — raw text misses the serving token distribution (`gen_calib --chat-template` does this).

**Experimental — synthetic mix with coverage stopping:** [Recover-LoRA](https://arxiv.org/abs/2606.04238) showed 10k *synthetic* samples match curated data for distillation recovery, and [NVIDIA's QAD](https://arxiv.org/abs/2601.20088) showed teacher logits transfer across domains — while our flat-routing measurement (§0) says 145 samples can't reach every expert. `python -m alis_dwq.gen_calib --model <teacher> --out dwq_data --mix EN=0.3,code=0.25,ZH=0.45` self-generates the jsonl, watches expert coverage through the routing hooks, stops when coverage plateaus, and drops degenerate generations via the loop detector. Scale anchor: the NF3-hybrid's per-expert GPTQ used **≈23k routed tokens per expert** on this 753B family — our 145-sample mix is ≈10× short of that; the tool reports median/p10 routed tokens per expert against this reference (reachability plateau ≠ sufficiency).

### 1a. Scan code entropy (student-only, minutes — decides whether 1b is worth the disk)

`python -m alis_dwq.code_entropy --model <student> --save entropy.npz` recovers every tensor's code histogram (through `mx.dequantize`, no source needed) and reports **effective vs nominal bits**: a group whose min-max grid got stretched by one outlier keeps most weights in 1–2 interior codes — nominal 2 bits, effective 1.x. Low-utilization tensors are exactly where `clip_quantize` pays off, so run this before hauling a multi-hundred-GB source onto the box; per-layer effective-bpw also feeds bit reallocation, and anchor-mass tracks the super-weight sites. (Lens borrowed from [lossless BF16 compression](https://github.com/brianbell-x/weight-compression): measure the information the bits actually carry.)

Add `--per-expert` (experimental) to break expert stacks out along axis 0 (bits ≤ 4): per-expert code entropy is the student-only proxy for **per-expert quantization damage** — the selection criterion the NF3-hybrid v3.6 validated after frequency saliency failed on this family (see §0). Outputs the most-damaged (tensor, expert) list: bit-promotion targets, or routing targets for `gen_calib`.

Measured reference (GLM-5.2 E1r 2.3 bpw, 2026-07-15). Two facts the aggregate report hides:

- **Expert damage lives in `down_proj`, and in the early layers' tail.** 93 of 19,200 down_proj experts sit under 70% utilization (gate/up: zero; MLA embed_q/unembed_out stacks: 93% healthy); medians are flat across depth (82.6%) but the extreme tail is all L3–L6 (worst: L3 expert 2 at 45.9%). The bit-spending prior "late layers matter" does not describe where 2-bit *grid damage* concentrates — consistent with the early-layer CKA/routing note in §3.
- **Container constraint on the "bit-promotion" use:** MLX packs an expert stack as one tensor with uniform bits, so per-expert promotion is not shippable in-place — the actionable lever for the damaged list is `gen_calib` routing targets (give those experts calibration signal), or an unpack-style layout change (cf. the MiniMax shared-expert note below).
- **Clip's mechanism, verified on the real artifact:** the same E1 student before vs after anchor-guarded clip-search: effective code payload **1.649 → 1.705 b/w, and all 225 of 225 expert tensors improved** — the utilization gain that decoded to the measured −6.1% raw wikitext PPL (part 2 of the E1 case study). Low code entropy predicting clip payoff is now a measured, not hypothesized, relationship on a 745B artifact.

### 1b. Clip-search requantize the student (free KL, before any training)

MLX's affine mode maps each group's exact min/max onto the grid ends, so one outlier stretches the whole group's grid. Borrowing the [four-over-six](https://humansand.ai/blog/nvfp4-rl.html) idea (narrow the range per block only when *measured* reconstruction error drops):

```bash
python -m alis_dwq.clip_quantize \
  --source <bf16/fp16 dump, or a Q8 dump with --dequantize-source> \
  --model <student> --out <student-clip> --max-err-slack 1.1 \
  --require-no-skips
```

The transaction always binds both canonical input-directory digests and
recomputes them before publication to detect mutation during lazy-mmap
processing. When Laguna conversion plans are present, both are required and
their plan hashes and pinned lineage must match: the source must be the
unquantized `bf16-mlx-layout` recipe and the student must be quantized,
unclipped, and pre-DWQ. Generic MLX inputs without Laguna plans retain the
original digest-bound workflow and the numeric lattice guards below.

Tries a few clipped ranges per group and accepts one only when it lowers the group MSE **without raising the group's max abs error beyond `--max-err-slack`×** the unclipped grid's (unclipped is always a candidate). Per-tensor bits/group_size are inferred from shapes, so dynamic recipes pass through untouched. **Run it before DWQ, never after**: DWQ trains scales/biases with the packed codes frozen, and re-deciding the codes is exactly what clipping adds (it would also discard an existing DWQ, since everything is recomputed from `--source`).

Two hard-won constraints (mechanisms + numbers in the [E1 case study, part 2](examples/glm-5.2-e1-floor-spike/README.md)):

- **The source must be quasi-continuous** — bf16/fp16, or a ≥8-bit dump via `--dequantize-source`. A dequantized low-bit lattice (nvfp4, ≤4-bit affine) as source produces correlated rounding that kills the model while every per-tensor metric improves (measured: identical rules, nvfp4 source → wikitext 51–12,769; Q8 source → 4.42–4.68). The tool refuses lattice sources unless `--allow-lattice-source`.
- **Keep the anchor guard on** (`--max-err-slack`, default strict 1.0; 1.1 measured best on a 2-bit student). MSE-only selection saturates the group-extreme "super weights" that min-max grids protect — mean −24% with anchors ×4 worse decoded to PPL 51.

**Experimental — outlier-scattering FFN permutation:** `--permute-ffn` attacks the stretched-grid pathology at the cause instead of the symptom. The FFN hidden axis is residual-free, so permuting gate/up **output** channels together with down_proj **input** channels (per-expert in stacks — the permutation closes inside each expert) is *mathematically identity* at zero runtime cost, while re-dealing which channels share a quantization group: channels are sorted by magnitude and dealt round-robin so every group gets an even outlier share ([PeRQ](https://arxiv.org/abs/2601.22347): calibrated permutations recover most of the full-rotation benefit at 2-bit). Unlike rotations, values are untouched, so the super-weight/anchor lesson above is not violated. Float sources only (blocks with a quantized source, missing member, or ffn-axis bias are skipped whole; a planned block that later fails aborts the run rather than de-align). Perms are saved to `<out>/ffn_perms.npz` for audit. Gate on held-out PPL + `code_entropy` before/after.

First A/B (2026-07-15, Qwen3.6-27B from bf16, FFN 2-bit/gs128 + rest 8-bit, 512-window PPL): **clip alone pays, permute on top did not** — naive → clip: wikitext 11.19→9.91 (−11%), code 3.23→3.04, ZH 17.12→15.80; clip+permute vs clip: PPL neutral-to-worse (9.96 / 3.04 / **16.13**, ZH +2.1%) while KL-vs-FP16 improved on all three slices (0.62/1.76/0.97 vs 0.66/1.84/1.00). Metric conflict resolves by the house rule: held-out PPL gates, so **permute is not adopted for this recipe class**. Scope caveat: this testbed's grids were already healthy (91% utilization — vs 80% on GLM E1-raw, where clip bought −6.1%), so the permutation had little stretched-grid pathology to fix; re-run the A/B on a low-utilization artifact before writing the idea off.

### Where to spend bits (measured, from the 4-bitter Lesson Fig. 18)

1. **Shared experts first** — near-free (+0.2 GB on a DeepSeek-style model) and the steepest single quality gain; they run for every token.
2. **Then the last ≈15% of layers** (returns taper: 4% → 8% → 15%).
3. **Don't bump the first layer** — ≈1 GB for no measured gain; reclaim those bits for 1–2.
4. **Recurrent/linear-attention state projections are a chokepoint** (KDA/GDLA `wkv_a`-class tensors, low-rank decay/gate producers): the state carries the whole sequence, so floor-bit codebooks there cap everything downstream — keep them high-bit regardless of the global recipe (Solar-Open2 audit, [case study](examples/solar-open2-250b/README.md): 36 layers of 2-bit state projections = the floor build's structural weakness, fixable for +96 MB). Same class: **router weights + expert biases** (discrete top-k flips), **untied embed/lm_head** — doubly so with a non-English tokenizer facing a language-consistency eval.

Cross-check the split against your own `expert_traffic` numbers before committing a recipe — and put the recipe *in the predicate*, not in a doc comment: a "CLI global + router override" predicate silently flattens any per-group intent (Solar's floor shipped flat 2-bit under a runbook that said otherwise).

### 2. Dump teacher targets (teacher's only appearance)

```bash
python -m alis_dwq.run \
  --model <teacher> --targets-only --target-dir ./targets \
  --num-samples 145 --max-seq-length 512 --batch-size 1 --seed 7
```

The dump is written to a sibling staging directory and published only after
all batches and `target-contract.json` are complete. The contract binds the
data-manifest hash, tokenizer files, teacher identity/revision/checkpoint
digest, selected row hashes, final token IDs, actual length-sorted/seeded batch
order, and every target checksum. A later run recomputes all live bindings
before loading a model and rejects partial, reordered, or replaced targets.
Creation and reuse also validate safetensor keys and metadata, the exact
pad-to-32 batch/sequence shape used by pinned mlx-lm, finiteness, nonzero
payloads, integer indices, per-token top-k uniqueness, and vocabulary bounds on
CPU. Release workflows must
still retain a standalone numeric-target manifest for independent receipt
verification.

To backfill this contract beside an older complete dump without touching any
numeric target file:

```bash
python -m alis_dwq.target_contract \
  --data-dir ./dwq_data --tokenizer <teacher-or-identical-tokenizer> \
  --teacher-checkpoint <teacher-checkpoint> --target-dir ./targets \
  --teacher-identity <repo-or-stable-id> --teacher-revision <immutable-revision> \
  --num-samples 145 --num-valid-samples 32 --max-seq-length 512 \
  --batch-size 1 --top-k 1024 --seed 7 \
  --tokenization preformatted_chat
```

The helper uses exclusive creation and refuses an existing sidecar.

### 2b. Distributed target dumps are not contracted

`alis_dwq.run` deliberately rejects `--pipeline` and any multi-process target
creation. A pipeline host sees only its local layer shards, so hashing rank 0's
directory would falsely label a partial checkpoint as the complete teacher.
Release-complete target evidence requires one process with the full checkpoint.
[`examples/distributed_dump_entry.py`](examples/distributed_dump_entry.py) is
retained only as a fail-closed legacy entrypoint; it does not bypass this
provenance boundary.

The notes below describe historical upstream pipeline debugging, not a supported
ALIS target-contract recipe. A future distributed contract must aggregate every
rank's owned-file manifest, prove completeness/no overlap, and bind every rank's
runtime and code before this path can be re-enabled.

Two gotchas cost us a full session on the first real distributed dump (790 GB 8-bit GLM-5.2 teacher across two 512 GB boxes; single-node teachers never hit this path). Both surface **identically** as `[METAL] Command buffer execution failed: GPU Timeout` on *one* rank even though the compute is fine — `eval_every`, wired-limit, and warmup are all red herrings. Diagnose by tracing per-layer (`mx.eval(h); print` after each layer, **both** ranks): you'll see one rank finish every layer while the other never enters its loop.

- **Every box needs the embedding shard — not just the first-stage rank.** The pipeline forward runs `embed_tokens(x)` on *all* ranks (later ranks discard it and overwrite with the `recv`). A rank missing the embed weights hangs at the embedding; its peer then trips the watchdog waiting at the collective. Replicate `embed_tokens` to every box; `lm_head`/final-norm only need the last rank.
- **`mx.eval` the pipeline's final `all_gather` before any GPU op consumes it.** The collective is on the CPU stream (no watchdog) — but the final norm/slice that reads it runs on the GPU, so the GPU command buffer *waits* on the collective while the slowest rank finishes its whole forward. On forward #1, which includes cold Metal kernel compilation on the deep rank, that wait blows past the macOS ≈5 s GPU watchdog and kills the rank that arrived first. Fix in the `deepseek_v3`/`v32` pipeline path: `n = h.shape[0]; h = all_gather(h, stream=cpu); mx.eval(h); h = h[:n]` — capture the local batch **before** `all_gather` grows axis 0. (Miss that and the dump silently saves `(ranks, seq, k)` logits — half of them the wrong rank's partial forward — instead of `(1, seq, k)`; slice back to row 0, the last-stage rank that owns `lm_head`.)

**Keep `--batch-size 1` identical between the dump and the training run.** Targets are keyed by batch index, so a dump/train batch-size mismatch silently aligns teacher logits to the wrong samples. Batch 1 also keeps each command buffer small — batch 8 at seq 512 is 4096 tokens/layer and flirts with the same watchdog.

### 3. Train the student, layerwise

```bash
ALIS_DWQ_LAYERS_PER_ROUND=8 ALIS_DWQ_DATA_DIR=./dwq_data \
python -m alis_dwq.run \
  --model <student> --quantized-model <student> \
  --target-dir ./targets --mlx-path <out> \
  --num-samples 145 --max-seq-length 512 --batch-size 1 \
  --grad-checkpoint --learning-rate 1e-6 --seed 7
```

(`--model` only supplies the tokenizer when targets exist — point it at the student; the teacher's 400 GB never move again.)

Memory stop gates are on by default for both target creation and training:
90% of MLX's recommended wired working set and at most 16 GiB of added swap.
They are checked after every target batch, training step, and validation step.
Set `ALIS_DWQ_MAX_PEAK_FRACTION` or
`ALIS_DWQ_MAX_SWAP_INCREASE_GIB` to a value `<= 0` only when intentionally
disabling that gate, and retain the memory JSONL as evidence. Set
`ALIS_DWQ_RUN_EVIDENCE_PATH` for a no-clobber two-event run JSONL that binds the
pre-DWQ checkpoint, target contract, and final artifact digests.
The launcher exclusively reserves `ALIS_DWQ_MEMORY_EVIDENCE_PATH` before any
model or checkpoint work as well, so every run must use a new memory JSONL and
cannot append to evidence from an earlier attempt.
Validation and round-decision lines on stderr record binary64 metrics with 17
significant digits. This preserves the exact `rv > best` rollback ordering for
receipt verification; the live training progress display remains rounded to
four decimal places for readability.
The student is saved into a run-owned sibling staging directory and published
to `--mlx-path` only by an atomic no-replace move, so concurrent runs cannot
mix or overwrite shards.
Before completion the launcher revalidates persisted calibration/tokenizer
files, all target semantics and hashes, and fresh teacher/pre-DWQ directory
digests; long-run input drift therefore emits only incomplete failure evidence.

`ALIS_DWQ_MAX_ROUNDS` and `ALIS_DWQ_MAX_STEPS_PER_ROUND` are diagnostic only.
Such runs require `diagnostic` in `--mlx-path`, write an incomplete marker into
the artifact, and never emit release-complete evidence.

**Experimental — LoRA error compensators:** `ALIS_DWQ_LORA_RANK=8` wraps every quantized module in a LoRA adapter ([Recover-LoRA](https://arxiv.org/abs/2606.04238) recovered 80–95% of 2-bit damage; [MiLo](https://arxiv.org/abs/2504.02658) is the MoE variant) and trains adapters alongside scales/biases under the same rounds/rollback. This adds the degree of freedom scales/biases (a per-group linear remap) fundamentally lack — the main lever left for the ≈2.3 bpw floor builds, and it may reopen sharper teachers for low-bit students (the sweet-spot failure was a student-capacity limit). Adapters are saved to `ALIS_DWQ_ADAPTER_DIR` (default `alis_adapters/`) in mlx-lm's `--adapter-path` format; **the saved checkpoint stays stock** — wrappers are removed before mlx-lm writes it. **The contracted `alis_dwq.run` launcher rejects a nonzero `ALIS_DWQ_LORA_RANK`**: the adapter directory is not yet transactional and is not bound into the final artifact digest, so a run that emitted release-complete evidence with adapters present would be claiming provenance it does not have. Re-enable it there only once the adapter directory has its own no-clobber transaction and is bound into run completion. Never fuse adapters into a quantized base (fusing requantizes = re-rounds the codes).

**Experimental — CKA drift monitor:** `ALIS_DWQ_CKA_MONITOR=1` reports per-round layerwise CKA between accepted states on a fixed valid batch (diagnostic only, ≈2 extra forwards/round). Rationale: [CKA-QAD](https://arxiv.org/abs/2606.05682) showed KL-only distillation can degrade internal geometry *while outputs match* — the same valid-vs-held-out inversion we measured twice (8-bit-teacher 2.56 bpw arm; router-KD arm). A round that valid-KL accepts but that craters one layer's CKA is the signature to investigate before shipping. Reading tip: weight **early-layer** drift heaviest — routing is largely decided by the upstream residual stream ([pulsar](https://github.com/giannisanni/pulsar) prefetches by running layer N+1's router on layer N's input, and it works), so early-layer CKA drift is a routing-path damage signal for *every* layer downstream; it also explains why retraining router weights alone (router-KD) bought nothing.

**Experimental — alternative distillation losses:** `ALIS_DWQ_LOSS=rkl|cakld|kl_top_K` swaps the training objective (default `kl` keeps the stock forward-KL call path unchanged). Ported from [AngelSlim](https://github.com/Tencent/AngelSlim)'s distill loss zoo (`angelslim/compressor/distill/loss.py`) — the Tencent QAD stack that independently converged on scales-only KD at lr 1e-6. `rkl` is mode-seeking reverse KL; `cakld` blends forward/reverse per token by the teacher's confidence on the ground-truth next token (BitDistiller-style — with a top-k target dump, a label outside the dumped top-k gets conf 0 = pure forward KL); `kl_top_K` restricts+renormalizes the loss to the teacher's top-K columns and is only meaningful with *dense* targets (a top-k dump already is this loss, and the tool refuses the combination). Rationale for trying `cakld`/`rkl` on the ≈2.3 bpw floor builds: forward KL is mass-covering, and a capacity-starved student spreading mass over the teacher's full distribution is the sweet-spot failure mode we measured — a mode-seeking term may spend the 2-bit budget better. Math selftest: `python -m alis_dwq.losses`. Unvalidated on-device; gate on held-out slice PPL/KL as always.

**Experimental — router-KD:** add `ALIS_DWQ_TRAIN_ROUTERS=1` to also train each round's router gate weights (matched by `(gate|router)$`, e.g. `MoEGate.weight`) alongside scales/biases. Rationale: quantized experts change outputs, so the original routing is no longer optimal — [0xSero's REAP 504B](https://huggingface.co/0xSero/GLM-5.2-504B) recovered a 34%-expert prune to eval parity by distilling *only* the gates (0.016% of params); quantization damage has the same routing-shift component. Routers are tiny, so memory cost is nil, and the per-round rollback still gates every change. Judge on held-out PPL/KL as usual — routing changes which experts fire, so training loss alone can mislead (see the sweet-spot note below).

**Experimental — per-slice acceptance gate:** `ALIS_DWQ_VALID_SLICE_MANIFEST=<json>` + `ALIS_DWQ_EN_GATE_EPS=<0..0.25>` (set together or the run refuses; requires `--batch-size 1`). The stock keep-best gate is one token-weighted scalar over the whole valid set — on Solar-Open2-250B it accepted a round that improved overall valid −14.6% while regressing the EN slice +4.4% KLD, because the high-loss slice (KO, ≈2.4× EN per-token) out-weighed it ([autopsy](examples/solar-open2-250b/README.md)). With a manifest (per-ordinal slice label + input/target sha256, fail-closed), `validate()` returns per-slice losses and a round is kept only if overall improves **strictly** (ties now revert) **and** EN stays within init×(1+ε). Off = byte-identical legacy behavior. Two caveats measured there: slice labels must describe actual loss tokens (self-generated rows are ≈86% continuation — corpus tags lie), and small-valid ε is weak (at σ≈4.5%, ε=1% still passes a true +4.4% regression ≈23% of the time) — the endgame is gating on a full-vocab T=1 sentinel of the slice you ship, not on the training surrogate.

### 4. Evaluate on language slices, not just overall

```bash
python -m alis_dwq.eval_kld --model <teacher> --save-ref ref.npz   # once
python -m alis_dwq.eval_kld --model <out> --ref ref.npz            # per build
```

Reports KL and top-1 flip per EN/code/ZH third (drop your own corpora in `data/`). Overall averages hide exactly the damage you're trying to fix.

**Experimental — degeneration probe:** add `--loop-probe 256` to greedy-generate 256 tokens per slice and report distinct-4gram ratio + tail-cycle detection. Motivation: REAP's 504B held *eval parity* while its loop rate doubled (3.6%→7.2%, z≈5) — aggregate scores hide behavioral degeneration the same way they hide slice damage. Cheap to run on every build; treat a new `LOOPED` on a previously clean slice as a ship blocker until investigated.

**Experimental — KV-tolerance probe:** add `--kv-probe 4` to also report the self-KL a 4-bit KV cache induces vs this model's own FP16-KV run (per slice; DSA/recurrent layer caches without a quantized form stay FP16 and are counted). Motivation: Bonsai 27B measured low-bit-weight models absorbing 4-bit KV **12–95× better** than FP16/Q4-weight builds — if DWQ'd students inherit that tolerance, long-context memory drops ≈4× as a free deployment win worth stating on the model card.

Measured (2026-07-15). Cross-family, the Bonsai phenomenon reproduces strongly (per-slice 9–145×, aggregate 56× — see the [audit](examples/bonsai-27b-audit/README.md) for why the aggregate flatters). In-family on our GLM-5.2 quants, self-KL orders with student bits — **2.3 bpw 0.079 → 2.56 bpw 0.113 → 3.5 bpw 0.143** (kv 4-bit gs64) — but read it as descriptive, not causal: top-1 flip is *not* monotone (8.9% / 13.0% / 12.1%), n=3, and the three builds differ in teacher and clip history as well as bit-width. Two takeaways that do survive: (a) PTQ+DWQ students show nothing near Bonsai-class KV immunity — whatever produces that immunity (their conversion process; see the audit's bounded Tier-2 verdict) is not a low-bit-container property; (b) ZH is the most KV-sensitive slice on every build (0.122/0.186/0.245 vs EN 0.074/0.096/0.105) — quantized-KV serving hits the language slices hardest exactly where weight quantization already does.

**Gate caveat — selective collapse hides in short-form metrics.** Sub-4-bit damage concentrates in *long* reasoning chains: Bonsai's cross-family data shows IQ2_XXS holding MMLU (88.9) while AIME collapses 93→57. Our KL/flip slices and the loop probe are short-form; a build can pass both and still have lost long-CoT. Until a long-form reasoning probe ships here, treat KL/flip parity on an aggressive build as necessary, not sufficient — spot-check a few long thinking-mode problems before shipping a new low.

## Model card & release

Publishing the quant is its own minefield — HF's card renderer and badge logic have several silent failure modes (a mixed-precision build badging at the wrong bit-width, a bare `~` striking through prose, special tokens eaten as HTML). The pre-publish checklist lives in [docs/MODEL_CARD_CHECKLIST.md](docs/MODEL_CARD_CHECKLIST.md): each item carries the *why* and the *fix*, plus a grep/awk battery to run before every card goes public.

## Hard-won operational notes

- **Gate disk as well as RAM between sequential arms.** Two ≈330 GB DWQ outputs back-to-back filled the volume to 100% and the second arm died at shard-write time ("Unable to write N bytes") — after 6 h of training layerwise cannot resume, so the whole arm re-ran. Check free space >= output size + margin before every arm, not just at campaign start.
- **A passing gate can ship a slice regression.** On Solar-Open2-250B the accepted round improved global valid −14.6% while EN KLD regressed +4.4% — the keep-best scalar is token-weighted, and the highest-loss slice (KO at ≈2.4× EN per-token) dominates it. If you ship per-slice numbers, gate per-slice (see the manifest gate in §3), and re-measure accepted builds on the *ship* metric before believing the valid scalar: the top-1024/T=2 training objective is a surrogate for full-vocab/T=1 KL, and the two can move in opposite directions on one slice.
- **Valid-set slice labels are seed-origin, not loss-token language.** Self-generated calibration rows are ≈86% model continuation — a "KO" row can be mostly English thinking tokens. Reconstruct labels from actual token spans (hash them) before gating or reporting on slices.
- **Reproduce before you believe.** Every headline number in the Solar case study was re-run independently and matched bit-for-bit (deterministic pipeline; the printed `±` is the standard error of the position mean, not a rerun σ). A number you haven't reproduced is a hypothesis.
- **Gate every big load**: wait until `free+inactive > model + 60 GB` *and stable* — a "done" log line doesn't mean the previous process released its memory, and loads launched into a reclaim window get jetsam-killed silently.
- **Never overlap a 100 GB-class load with heavy disk I/O** (uploads, mass writes): the load wedges with rss/avail frozen. Kill (-9, then verify with pgrep — zombies squat memory), let it reclaim, relaunch on a quiet box.
- **Getting the teacher shards onto each box (distributed dump):** Xet-backed HF repos don't parallelize with `aria2c` — the `resolve/main` redirect is a byte-range-signed CAS URL, so multi-connection splits `403`. Use `snapshot_download` with `HF_XET_HIGH_PERFORMANCE=1` and per-shard `allow_patterns` to hand each box only its half. Xet can also silently wedge mid-repo (shard count frozen, zero net-in) — wrap it in a watchdog that kills + resumes when progress stalls. If one box's uplink is slower, have the faster box pull its peer's remaining shards and ship them over the local (TB/LAN) link.
- Learning rate transfers poorly across student sizes: 1e-5 was fine for an 87 GB student and diverged on a 242 GB one. Start at mlx-lm's default 1e-6; the per-round rollback makes over-stepping cheap.
- If your checkpoint carries extra layers your runtime remaps (e.g. an MTP head), you have two working paths. (a) Strip them for training with a hardlinked variant and re-attach after — **never edit a hardlinked file in place**; replace it (`os.replace`), or you rewrite the original through the shared inode. (b) Train with them attached (the model's `sanitize` remaps them at load) — but then the *saved* checkpoint carries **module-named keys** (e.g. `mtp.layer.*`) instead of the checkpoint convention (`model.layers.<N>.*`), and strict loading breaks with "N parameters not in model". Fix by inverse-renaming those keys in the affected shards + index; **verify the inverse map by asserting the renamed keyset equals the original checkpoint's** before shipping, and write via temp-file + `os.replace` (see the lazy-mmap note above). If a conventional-name copy of the module already exists (e.g. a previously shipped sidecar shard), a third path is cleanest: **strip** the module-named tensors from the base shards and re-attach the sidecar — then assert the stripped tensors **byte-match** the sidecar under the rename map. That equality check is a free integrity oracle: it simultaneously validates the map and proves the module passed through the whole quant/retune pipeline untouched.
- **Stock `mlx_lm.perplexity` / `mlx_lm.evaluate` never set the wired limit** — only generate/server do. On a 100 GB-class model that is a silent ≈10× slowdown (throughput thrashing, not an error). Wrap them: `mx.set_wired_limit(mx.device_info()["max_recommended_working_set_size"])` after load, then call the module's `main()`. (This repo's `eval_kld` already does.) Custom eval scripts loading an MTP-bearing checkpoint also need `load_model(..., strict=False)` unless the runtime remaps the head.
- **Choosing K (layers per round)**: backward memory scales with K, so pick the largest K that fits. Anchors from the 745B family on a 512 GB box: a 227 GB student at K=8 peaked ≈307 GB; a 310 GB student at K=6 peaked ≈389 GB. Start high, drop K on OOM — rounds get proportionally cheaper, total wall-clock barely moves.
- **A REVERTED round near the end is the gate working, not a failure.** Both shipped GLM retunes ended with one late-round rollback (best already reached); treat consecutive reverts as the natural stopping signal.
- When re-attaching a shard, **name it `model-*.safetensors`**: mlx-lm's loader collects shards by that glob, not by the index — a shard named anything else silently never loads and you get "missing parameters" for exactly its keys.
- **`mx.load` is lazy (mmap) — never `save_safetensors` back to the path you loaded from.** The save truncates the file *before* the lazy view is read, so you write zeros over your own data. `mx.eval` the new arrays first, or write a temp file and `os.replace`. (We zeroed a whole target dump post-processing it this way — and the real fix was to not post-process at all: get the shape right in the forward, per §2b.)
- **Verify a dump is non-zero and the right shape before you reclaim the teacher.** A distributed dump is your only local copy of the teacher's logits; the teacher weights are the cheap thing to reconstruct, the dump is not. After the corruption above we'd already deleted one box's teacher half — re-dumping meant re-pulling 400 GB. Keep the *peer* box's half until the targets pass a `min/max != 0` + shape check; and to free a box for the next stage, move the student to the peer over the local link (minutes) instead of deleting and re-pulling from HF (an hour).
- **Xet can also wedge after a device-level I/O interruption, not just mid-repo.** After a USB enclosure dropped and re-enumerated mid-download, `hf download` sat alive-but-dead — ≈0% CPU, trickle network, zero file writes — because the background writer thread had died (`Internal Writer Error: Background writer channel closed`) and the main thread waits forever. It reproduced twice in one day, once at 57/59 shards. The stall watchdog that catches it: downloader process alive **and** no file in the target tree modified for 10 minutes → kill and relaunch (resume is safe; completed files are kept).
- **VL MoE recipe note — check whether the shared expert is *packed* into the routed bank.** mlx-vlm's MiniMax-M3 packs the shared expert as expert #128 inside the same SwitchLinear when `shared_intermediate_size == intermediate_size`, welding the one tensor that sees **100% of tokens** (a routed expert sees ≈3% at top-4/128) to the routed experts' bit-width. Unpacking it and holding it at 8-bit while routed experts drop to 3-bit cost +0.4% size and needs only a config-gated layout switch ([mlx-vlm#1544](https://github.com/Blaizzy/mlx-vlm/pull/1544); packed vs unpacked forward matches to 7.75e-07). The same audit applies before DWQ: a packed shared expert can't be given its own learning treatment either.
- **Evaluating a thinking model: budget `max_tokens` for the thinking, and grade the tail.** A needle-retrieval probe with `max_tokens=30` "failed" 0/3 on an 8-bit reference — the model spent the whole budget inside `<mm:think>` and never emitted the answer; at 400 tokens it was 3/3 at every depth. Harness artifact, looks exactly like model damage.

### From a 2.8T ternary-codebook student (Kimi-K3 v3, 2026-08-02)

> The complete Kimi-K3 lesson set — architecture porting, campaign mechanics, custom Metal
> kernels, evaluation infrastructure, 2-box EP serving, and the operational pitfall catalog —
> lives in [docs/kimi-k3-mlx-port.md](docs/kimi-k3-mlx-port.md); raw receipts (router-mass data, decode-KL certification) in [examples/kimi-k3](examples/kimi-k3/README.md). The optimizer-arithmetic
> lessons below are the DWQ-relevant subset.

Four of eight 12-layer blocks diverged (train nMSE 3× within 24 steps, val +80…+500%) under a trainer we rewrote for a custom architecture. Five hypotheses were acquitted one by one — router training, codebook-scale training, a distribution-alignment loss term, the custom backward kernels (verified cos 0.99998 vs a chunked autograd reference at production shapes), the eval path (bit-stable across repeated evals) — before the real causes turned out to be two lines of optimizer arithmetic:

- **MLX `optim.Adam` defaults to `bias_correction=False`.** Effective lr is nominal × `(1−β₁ᵗ)/√(1−β₂ᵗ)`: peaks **6.6× at step 12**, still 3.3× at step 96. Our nominal 3e-6 was really ≈2e-5 — exactly the value our own earlier sweep had recorded as "diverges". The amplification profile (max at ~step 12, slow decay) *is* the "fast spike, partial recovery" signature. Upstream `mlx_lm/quant/dwq.py` sets `bias_correction=True` explicitly; any fork must too, or no lr number is comparable to anything.
- **bf16 trainables without an fp32 master copy don't train — they freeze or jump.** Adam's step size ≈ lr regardless of |θ|, but bf16 ULP ∝ |θ|: at lr 3e-6, every parameter with |θ| ≳ 0.01 receives **zero** net update over 96 steps (half-ULP swallow, measured end-to-end), while the near-zero tail moves in whole-ULP jumps of 1.5–3× the intended step. Which parameters sit where differs per block — hence "some blocks diverge, some silently learn nothing". Bonus pathology: **bf16(0.999) == 1.0**, so Adam's second moment never decays (a one-spike ratchet). Upstream dwq.py accumulates trainables in fp32 ("Accumulate learned weights in higher precision") for exactly this reason. Fix both by promoting trainables (and thus optimizer state) to fp32; cast back at save.
- **The meta-lesson: diff-audit the upstream trainer before shipping a rewrite.** Both omissions were sitting in plain sight in `mlx_lm/quant/dwq.py` (lines 152–156, 393). When a custom architecture forces you to fork a training loop, diff your optimizer construction, precision handling, and loss shape against the tool you forked line-by-line — invariants live in code you didn't copy.
- **Triage heuristic that found it**: correct gradients + divergence under *every* trainable-parameter subset + block-dependence = suspect the update arithmetic (θ ← θ − Δ), not the gradient path. Gradient checks cannot see rounding at apply time.
- **Port the monotone rollback everywhere.** Our fork kept "save best" but dropped the *revert-on-worse-val* gate this repo ships; diverged blocks then walked 70+ steps past their own cliff, wasting the whole arm. Pair it with a step-8 tripwire (train > 2× initial val → revert + halve lr).
- **Don't train the router.** Ecosystem consensus (llama.cpp refuses to even quantize `ffn_gate_inp`; unsloth disables router FT by default), and value-path-only gradients can't see the top-k selection flips they cause. In our case the router was *acquitted* for the divergence — but on layers where most experts are kept bit-exact, router-correction has no premise at all.

**Re-validation results (2026-08-03).** With the fixed recipe (fp32 masters + `bias_correction=True` + λ=0 + router off + rollback/tripwire), all eight 12-layer blocks trained cleanly — including the four that previously diverged — at val-KL deltas of −12.3…−36.8% (mean −24.1%, vs −18.7% for the old bf16 recipe on the blocks that survived it). End-to-end on the rebuilt 737 GB / 2.10 bpw student vs the same teacher-logit windows: **KL 0.349 → 0.225 nats (−35%), top-1 flip 17.7% → 13.8%, wikitext PPL 2.88 → 2.08 (−28%)** relative to the prior 948 GB / 2.71 bpw release of the same model — a strictly smaller build that is strictly closer to its teacher. One lr note: nominal 3e-6 *with* bias correction was the stable default across blocks; the one block that still tripped the val tripwire converged at 1.5e-6 after an automatic halve-and-revert.
- **Shipping a 200 GB-class build to HF: mind the private cap and the commit budget.** Private repos have a storage limit a big staging blows through mid-upload ("Private repository storage limit reached") — if the plan is stage-private-then-flip, either budget for it or flip public *first* and push the model card as a small commit before the weights, so the public page is never incoherent while shards land. Separately, `upload_large_folder` spends the 128-commits/hour budget on shard batches and grinds to a crawl with rate-limit retries; a single `upload_folder` commit avoids the ceiling entirely.
- **HF's card renderer pairs *single* tildes into strikethrough.** Two "\~90 GB … \~40 K" approximations in one paragraph render as a struck-through span (and can break `**bold**` parsing mid-pair, leaking literal asterisks). GitHub only strikes on double `~~`, so a card that previews fine on GitHub still corrupts on HF — escape every literal tilde (`\~`) in card prose.
- **Clearing `~/.cache/huggingface` deletes your auth token with it.** Public downloads keep working afterwards, so the loss surfaces only at the next upload as "Invalid username or password", hours later. Preserve the `token` file when reclaiming cache space (or expect to re-run `hf auth login`).
- **Publishing branch-per-quant on HF: branches inherit `main`'s files at creation.** Create branch → upload build = the branch now carries *both* builds' shards (ours had 39 stale + 87 real; snapshot downloads grow ≈190 GB). `delete_files` the inherited shard names on every non-main branch after upload, and verify per-revision shard counts via the API.
- **Swapping a build in-place with `upload_folder` leaves the *outgoing* shard set behind whenever shard naming changes.** `upload_folder` adds/overwrites, never deletes: a 3.5 bpw `main` silently carried 153 shards / 661 GB for four days (an older build's `model-*-of-00076` set next to the new `-of-00077` set). The repo still *works* — the index resolves to the new shards — but `snapshot_download` pulls both builds. Same-name uploads mask the issue (a later same-sharding build overwrites fully in place), so it surfaces only when shard count/naming shifts between builds. Detect with an index-vs-tree audit on **every revision**: `set(tree *.safetensors) - set(index weight_map.values())` must be empty per branch (branch snapshots inherit `main`'s orphans at creation — cf. the branch-inheritance note above). Prevent by making swaps **atomic**: one `create_commit` carrying the new files *plus* `CommitOperationDelete` ops for the outgoing set.
- **HF sidebar param count for quantized repos comes from `model.safetensors.index.json` metadata `total_parameters` — and `mlx_vlm.convert` doesn't write it** (`mlx_lm.convert` does). Without it the Hub counts packed-U32 elements as parameters and shows ≈1/8 of the truth (427B displayed as "56B"). Inject the exact count (summed from the bf16 source shard headers) before upload; verify with `api/models/<repo>?expand[]=safetensors`.
- **Never re-quantize a dequantized low-bit lattice with a coarser grid.** nvfp4/≤4-bit-affine dequants sit on a coarse lattice; a coarser min-max affine grid over lattice values rounds with correlated bias (continuous sources round pseudo-randomly), and the bias accumulates through activations — the model dies while per-tensor MSE, kernel outputs, and every artifact check look *better*. Paradox signature: the more groups you clip (off-lattice rescale), the more alive the model. Sources for requantization must be bf16/fp16/Q8-class.
- **When the master *is* the low-bit lattice, you have no choice — and DWQ is no escape.** The rule above assumes a bf16/Q8 source exists; an **INT4-master MoE** (Kimi-K2.7 / DeepSeek `compressed-tensors`, experts native INT4-g32 QAT) has none, so retargeting the bit-width *is* re-quantizing a low-bit lattice and the correlated-bias tax is unavoidable — Kimi-K2.7 3-bit-from-INT4 measured a **10.2% decisive top-1 flip** vs the 4-bit (≈ the original). DWQ can't rescue it: it needs a *higher-bit* teacher that by construction doesn't exist; the 4-bit sibling is same-source-family (so its KL is a valid within-family measure — cf. the de-resonance note below — but caps distillation at 4-bit info), and the distributed backward is blocked anyway (`[Primitive::vjp] Not implemented for Send`). So 4/6/8-bit are one quality shelf and the only real lever is bits, not scale. Two measuring traps: the raw compressed-tensors master is **not `pipeline_load`-able** ("only supported for MLX converted models") and OOM-kills single-box even lazily (>RAM → weights go resident mid-forward) — use a 4-bit MLX build as the runnable "original"; and never name an `mlx.launch` script flag `--n` (abbrev-clashes with `--nccl-port`/`--no-verify-script` → abort). Full negative-result writeup: [examples/kimi-k2.7](examples/kimi-k2.7/README.md).
- **A mean weight metric cannot see super-weights.** The few largest-magnitude weights per tensor do disproportionate work, and min-max affine grids protect them for free (they *are* the grid ends). Any transform that trades their fidelity for interior precision (MSE-optimal clipping at 2-bit: top-0.01% weights ×4 error, mean −24%) kills the model. Gate weight-space transforms on per-group max-error and held-out PPL, never on mean reconstruction metrics alone.
- **KL against a *quantized sibling* reference penalizes de-resonance — anchor quality judgments to real-text PPL.** A 2.56 bpw build re-derived from a Q8 source (clip) improved every held-out corpus (wikitext −2.0%, code −0.7%, tulu flat) yet its KL vs the 4.5 bpw sibling reference *rose* +10% (flips +1.5 pt): the previous build shared the reference's 4-bit-lattice ancestry, so it sat artificially close to it. Quantized-sibling KL is only comparable *within* one source family; across source classes it mistakes de-resonance for damage.
- **Hash the *resolved* file, not the HF `raw/` endpoint, when verifying tokenizer identity across repos.** `raw/` serves the ≈133-byte LFS pointer for LFS-tracked files, so the hash "mismatches" even when the tokenizers are byte-identical; download the real file and `shasum` that. `tokenizer_config.json` may also differ by benign client keys (e.g. `local_files_only`) — identity lives in `tokenizer.json`.
- **Start the decode timer after prefill, and keep Time Machine away from scratch trees.** Timing a generator from its first iteration folds prefill into "decode" and manufactures a fake long-context decode cliff (we chased one for a day). Separately, an unexcluded few-hundred-GB working tree gets picked up by Time Machine mid-run and strangles disk I/O — `tmutil addexclusion <dir>` every big build/download directory at creation.
- **A sandboxed autonomous agent cannot see the GPU.** macOS Seatbelt profiles (e.g. Codex CLI `workspace-write`) block Metal device access: MLX fails with `[metal::load_device] No Metal device available`, and detached/nohup children inherit the sandbox. Probe Metal *before* any download/build step in agent-run pipelines, and give GPU-touching agent runs full (unsandboxed) access — probe-first discipline turned this from a wasted 790 GB download into a zero-cost stop.
- **A sharper teacher is not always better — it depends on the student's bit-width, and only held-out PPL tells you.** Re-tuning a 3.5 bpw GLM-5.2 student against an 8-bit teacher (vs a 4.5 bpw one) improved held-out strided PPL a real, significant **−1.3%** (wikitext). The *same* 8-bit teacher on the more-quantized **2.56 bpw** student made it slightly **worse** (+1.3%, within noise) — even though its DWQ-vs-teacher loss dropped **35%**. At ≈2 bpw the student can't represent the finer target distribution, so chasing it overfits the 145-sample calibration set without transferring to the eval corpora. There's a **teacher-precision / student-capacity sweet spot**: a mid-bit student benefits from a sharper teacher, an aggressively-quantized one does not. Always judge on held-out PPL, never on the training/validation loss alone (which will happily drop toward any teacher).
- **Parity to a reference proves faithfulness, not correctness — and the *reference* can be the broken one.** Porting Motif-3-Beta to MLX, the published HF reference (SHA `32b0305`) could not run at all — three defects (yarn-rope `inv_freq` built from the wrong head dim; the GQA repeat missing from eager attention; expert-0's activation coefficients applied to all 384 experts, silently). A parity harness that agrees with a reference only proves your port matches *that* reference; point it at the fixed one, and gate "correct" separately from "faithful". Motif fixed all three after HF discussion #6 — full story in [examples/motif-3-beta](examples/motif-3-beta/README.md).
- **Garbage at position 0 is a position-independent bug — suspect the activation, not rope.** Motif's incoherence was present generating from a single BOS token, where the attention softmax over one key is 1 and rope/q·k are irrelevant. That one observation redirected the hunt off rope (YaRN + SWA + differential attention, the tempting suspects) and onto the activation, where the real defect lived: PolyNorm config keys (`polynorm_sigmoid_weight`, `polynorm_output_scale`, `polynorm_bias_clamp`) present-but-unread. Fixing just that took held-out NLL ≈23 → ≈2.1. Forward-math fixes touch no weights, so verify them by hot-patching the existing quant — no re-quantization. **But sort fixes carefully: a change to how weights are *produced* (`sanitize()`, a tensor split, the predicate) invalidates every earlier build.** Mis-filing one as forward-math is how this campaign shipped a corrupt 8-bit reference.
- **`mx.split` silently corrupts tensors over 2³¹ elements** ([ml-explore/mlx#3836](https://github.com/ml-explore/mlx/issues/3836)). Splitting the 8 GB fused `gate_up_proj` (a >2³¹-element bf16 tensor) returns garbage past the 4 GiB offset (from ≈expert 205/384); strided slices are correct. Slice, don't split, any large fused-expert MoE. Reported-but-unfixed on mlx 0.31.2 / 0.32.0.
- **A KL anchor is load-bearing for every number measured against it — verify it by generation first.** The Motif 8-bit reference shipped on a smoke test that predated the campaign's own `mx.split` fix (the fused expert tensor is 1.88× the 2³¹ limit, so the split silently corrupted everything past the 4 GiB offset). It loaded, passed shape/index checks, showed healthy per-tensor statistics, and quantized to byte-identical size — and produced infinite repetition at greedy decoding. Because it was also the ladder's KL reference, every `KL vs Q8` figure and the "DWQ cut KL 58–72%" claim had to be withdrawn from the published cards; the models were fine, the measurements were not. Two habits fall out: **generation-verify every shipped tier, not just the headline one**, and **when a weight-materialization fix lands, enumerate every artifact built before it**. Also sample forensics where the bug is — first-pass statistics over experts 0–3 looked perfectly healthy; corruption started at expert 205. Full postmortem in [examples/motif-3-beta](examples/motif-3-beta/README.md).

- **Clip and DWQ fix different failure modes — gate on generation *and* KL.** On the Motif 2-bit floor build, anchor-guarded clip lifted the code slice out of a hard loop (distinct-4gram 0.011→0.054, KO 0.13→0.86) while KL-vs-reference barely moved; DWQ then cut KL −58 to −72% on top. Clip's win lives in generation space (degeneration), DWQ's in distribution space (KL) — a build gated on KL alone would have shipped the looping raw floor. (The generation-space twin of the quantized-sibling-KL note above.)

- **MLX `gather_qmm` autograd has a two-term memory law — shape the backward to it, don't fight it.** (1) scale/bias grads materialize the *full dequantized extent of whatever you differentiate* → slice the expert axis of the live tensors; (2) activation grads materialize *one dequantized expert matrix per routed assignment* → serialize over token blocks; and (3) fp32 scales pushed into the module make even *forward* fall off the fused kernel (2× peak). A 256-expert bank whose fused backward wants 150 GiB runs at 24.9 GiB with grad cosine ≥0.9985 — decomposition, measured tables and the exact `out + (live − const)` replay trick in the [Inkling streamed-backward case study](examples/inkling-975b-streamed-backward/README.md). Two traps inside it: grouping within a *single* lazy graph does not cap the peak (all groups' slice-scatter grads coexist at eval — serialize with `mx.eval` per micro-backward), and write the replay as `out + (live − const)` (exact zero delta), never `(out − const) + live` (fp reassociation shifts the loss).
- **Thousand-backward loops drift the MLX allocator cache past RSS/footprint guards.** A seq-3234 streamed round grew from ≈25 GiB active to >96 GiB *held* — healthy model, tripped watchdog. `mx.set_cache_limit(8 GiB)` around the loop (restore in `finally`) pins footprint at active+8 GiB. If your harness kills on footprint rather than swap, this is load-bearing.
- **The differentiable forward and the inference forward are different deterministic kernels** (≈0.2% loss difference on a real MoE layer, bitwise-stable each). Pin reported metrics to one path — receipts that mix them don't reproduce.
- **Sample the live process before theorizing.** `/usr/bin/sample <pid>` + `lsof` snapshots identified every real bottleneck of this campaign (allocator drift, per-assignment dequant, redundant re-verification) in minutes each; every hypothesis formed *without* them was wrong. Cheap, always available, works on sealed/isolated children.
- **Calibration sequence-length variance dominates layer-local wall-clock.** Batches spanning 140→3234 tokens make identical layers differ 50× in round time (memory-bounded streaming is flat in memory, linear in tokens). Budget on Σ(tokens) and set timeouts from the longest batch, not the mean — our driver's mean-based timeout killed a healthy 54-minute round.

### From a latency-bound decode campaign (Motif-3, 2026-08-14)

> The full campaign — speculative-decoding economics, the transition mega-kernel, oracle-first
> lever pricing, and the prefill ceiling analysis — is written up as Addenda 14–17 (+ postscript)
> in [examples/kimi-k3](examples/kimi-k3/README.md). These are serving-side lessons rather than
> DWQ ones, but they price what a quant is worth in production, and the measurement-discipline
> half transfers directly.

- **k-economics invert when decode is latency-bound — verify width is nearly free.** A 4-token verify forward costs only ≈1.5× a 1-token one (46 → 70 ms measured), so chained MTP drafting at **k=3 beats k=1 by ≈35%** on Apple silicon — directly inverting the vendor's "1 speculative token is optimal", which was derived in a compute-bound (vLLM) regime. Check which regime you are in before importing serving folklore. And **re-tune k after every big latency win**: as latency comes out, decode slides back toward bandwidth-bound and the optimum *shrinks* for fatter builds — the 8-bit tier moved k=3 → k=2 while 4.5 bpw stayed at k=3.
- **When a speculative chain underperforms, audit the normalization path before blaming the head.** Feeding chained drafts back through the backbone's final norm a second time — instead of the MTP block's own output norm — crushed chained acceptance enough to make k=2 *net-negative* (19.3 tok/s); fixing that one norm turned the same k=2 into **+15% (34.6 tok/s)**.
- **Glue fusion compounds.** After the Sinkhorn dispatch-bomb fix (the campaign's first single-kernel win), compiling the remaining elementwise glue — activation polynomials, router, mHC mixes, attention epilogue, all bit-exact and each kill-switched — added +5%, then another +9–11% on top: plain decode **20.2 → 24.5 tok/s (+21%)** from fusion alone. Individually unimpressive levers stack when each is bit-exact — but budget a **±5% acceptance-trajectory noise band** on MTP end-to-end numbers and adjudicate levers only above it.
- **A mega-kernel wins only over *small serial* ops.** Fusing large GEMMs into one threadgroup serializes the memory system — an earlier attempt on this same model failed exactly that way. Fusing the small-tensor bookkeeping *between* blocks — a 16K rmsnorm, a 24-output gate projection, 20 Sinkhorn iterations, the residual premix, the next layernorm, i.e. ≈7 serial dispatches per transition — into one threadgroup per position, with every large GEMM left outside, cut transition latency **175 → 84 µs** at verify width 4 and bought **+17% (4.5 bpw, 50.2 tok/s) / +21% (8-bit, 37.1 tok/s)** end-to-end. The corollary bounds it: folding the (multi-threadgroup-parallel) residual *postmix* into the same kernel measured neutral — removing a dispatch pays only when the removed op's lost parallelism is worth less than the inter-kernel gap.
- **Oracle-first: price a lever with a probe before you build it.** Two directed levers died on cheap measurement for the price of none. *Tree drafting*: a 768-step probe that just logs the verify target's rank in the existing draft logits showed rank-2 coverage of **11.6%** — the entire theoretical prize of a second branch — plus a 30% depth-2 conditional on the alternate branch vs ≈62% on the argmax branch, i.e. this head's misses are hard misses, not near-misses; upper bound **+4.7%** at zero cost, net negative once per-depth rope groups, KV compaction and a wider verify are paid for. Probe the drafter's rank distribution (half an hour) before building masks and cache surgery. *Fused norm→GEMV at verify width*: accuracy-correct, but at N≥2 a hand-rolled per-lane kernel loses **3–5×** to the library's simdgroup-matrix quantized matmul — a ≈14 µs stage-removal target buried under a ≈170 µs kernel deficit. Custom kernels earn their keep on N=1 GEMVs and non-GEMM bookkeeping; past N=1, join the library, don't fight it — and kill a lever *before* integration when its applicability window has already moved (k=3 made the hot path width-4, leaving an N=1 GEMV kernel touching only the tiny drafting side).
- **Measure the ceiling before chasing it.** Directed to push prefill "to the hardware limit", the first honest measurement said we were already at **63–70%** of it: the fusion stack built for decode had lifted prefill **143 → 575 (2k) / 751 (8k) tok/s** as a side effect. A chained three-way microbench (grouped-expert `gather_qmm` vs dense `qmm` vs bf16 GEMM at identical FLOPs) then located the entire remaining gap in one place — sorted `gather_qmm` runs at **≈69% of dense throughput** for MoE-typical ≈43-row expert groups (filed upstream: [ml-explore/mlx#4246](https://github.com/ml-explore/mlx/issues/4246); *unsorted* gather is a further **4.8× cliff**, so always sort). Chunk-boundary async was a null (+1%); the chunk-size sweep re-confirmed 1–2k optimal.
- **Two lazy-framework measurement traps that manufacture numbers.** (a) An ablation that returns *constants* (zeroed attention) silently disconnects everything downstream from the eval target — the "ablated" run measures an empty graph; ablate with value-preserving dependencies. (b) A benchmark loop without a serial dependency between iterations evaluates one iteration out of N — we briefly "measured" **178 TFLOPS on a 28-TFLOP GPU**. Chain every microbenchmark. (Same family as the prefill-in-the-decode-timer trap above.)
- **Benchmarking MoE prefill: state the prompt's routing entropy, and separate cold from warm.** A prefill scatter that looked like thermal throttling or a code regression was *prompt content*: interleaved same-process runs measured **545 tok/s** (short repeated sentence), **757** (longer repeated), **790** (varied natural text) — a **45%** end-to-end swing driven entirely by expert-routing skew fattening the small-group tail in `gather_qmm`. A repeated-sentence benchmark measures the worst case, not the typical one. Separately, first-touch residency costs a 312 GB build ≈2.4 s, which silently halved one published number — report cold and warm apart. Both findings are now part of the upstream report.

### From a hybrid-VL conversion + decode campaign (Qwen3.8-27B, 2026-08-15)

> The full campaign — multimodality-preserving conversion, the MTP double-shift, the
> quantized-GEMM small-`M` gap, the split-K kernel, and the speculative-decoding verdict
> *and its reversal* (the superseded verdict is kept in place: the reversal is the more
> useful half) — is in [examples/qwen3.8-27b](examples/qwen3.8-27b/README.md), with the raw
> receipts (`m_*.json` per-build records incl. the full top-1 id sequences, the `kv_*.json`
> sweep, `measure.py` / `table2.py` / `kv_measure.py`, and the AIF verdict ledger).
> The reusable half — the same rules generalized off this model, each with a runnable
> oracle — is the checklist in [docs/PORTING_INTEGRITY.md](docs/PORTING_INTEGRITY.md).
> These sit next to the MiniMax-M3 shared-expert note as *conversion-integrity* lessons:
> what a converter throws away before any quantization decision is made.

- **Offloading part of a quantized model to a second accelerator is decided by six numbers, and four of them come before any benchmark.** A machine with an idle matrix unit next to the GPU — Apple's Neural Engine, an NPU, a DSP — invites splitting each linear so both work at once, and the wiring is often already written. We measured one such path end to end, **refused it for the wrong reason, then took it**: driven through the vendor's own entry sequence it delivers **+26% prefill at 99.95% top-1 agreement**. The method transfers either way: **the roofline share** (a memory-bound phase at 77% of its bandwidth ceiling cannot be helped by a unit that adds arithmetic through a narrower memory port — we closed decode on arithmetic alone, no benchmark), **the precision floor** (`(max/rms)/(127*sqrt(12))` for per-channel INT8 — our weights were Gaussian at max/rms 3.99, so the floor was 9.1e-03 and we measured 8.75e-03, which told us immediately that clip search, AWQ and rotation had no outliers to grip: they bought 1.9% and 0.04%), **the simulator's fidelity** (model the accelerator's quantizer in-framework and validate it against hardware — ours matched to three significant figures, turning a 0.2 s-per-compile grid search into seconds), and **the cliff location** (sweep *past* the throughput peak; past it the accelerator becomes the critical path and the step waits on it). The remaining two are quality gates and they are the ones vendors get wrong: **never evaluate an approximate path with cosine similarity** (`cos ~= 1 - err^2/2` renders a 4.5e-03 relative error as 0.99999 — honest, and it hid sixty-four layers compounding into 1.6% top-1 agreement), and **report mean KL over every position next to top-1 agreement**, because single-position KL is chaotic (ours fell as we added error, which is impossible) and KL alone passed a configuration that flipped the argmax on 6.7% of positions. Two operational rules ride along: **a "no difference" result is not evidence until a counter proves the change ran** — five silent no-ops on this path each succeeded, logged nothing, and did nothing, and twice the silence read as good news — and **test for first-execution bugs explicitly** by running the same program twice, since a result that is wrong on first read and right on re-read is an ordering bug, not a precision one. Three lessons came out of the reversal itself. **Reproduce through the vendor's entry sequence, never around it** — our harness called the enable function directly and skipped a load-time warm-up of every compiled program, so each program's first execution returned garbage and we published that as precision loss; the correct path logs `Warmed N procedures` and we never checked for the line's absence. **Some of the gain is in the loader, not the accelerator** — nine of our twenty-six points came from a layout call that must run before the weights load, invisible to every accelerator counter. And **a second lever does not multiply with the first, it competes with it**: composing the offload with a two-machine pipeline worth 1.9x gave +10.6% at a 32K prompt and **-3.9% at 8K**, because relieving compute promotes link transfer and erodes the pipeline ratio (1.90 -> 1.80) — multiply two separately measured gains and you predict a number that does not exist. **Decompose the crossover before explaining it**: we first credited it to chunk count amortising the pipeline bubble, and an offload-off control showed the wide chunk never wins without the offload at any length — the bubble cost does shrink with length (-9.8% to -1.9%) but only the offload gain (+4.7% to +13.4%) carries it over the line. Then **set the threshold where the gain clears the noise, not where the sign flips** (ours crossed near 9216 tokens but tied through 10240, so we shipped 11264), and **ship the switch as opt-in while baking the measured value** — without the accelerator the branch is a pure loss. **A competitor's quantization scheme is readable from its public artifacts, and only half of it is transferable.** GGUF stores its tensor table at the head of the file, so HTTP range requests over a 14 GB quant return the whole bit assignment without downloading it; several budget points diffed against each other give the scheme's priority order. Doing that to Unsloth's Dynamic 3.0 separated two halves: an imatrix-driven part (their FFN widths track their own per-channel activation statistics at r = 0.65-0.78) and an arithmetic part (attention V and K sit high at every budget because under GQA they are 0.33% of the parameters each — cheap, not precious). Only the arithmetic half transferred: promoting five cheap tensors plus the output head was worth **−16.6% KL on top of our published AWQ build** (paired, t = −30.8), while every version of their allocator we rebuilt lost to plain uniform. Three controls make that claim survivable — **spend the identical bytes on arbitrary tensors** (bought −1.2% where the chosen five bought −17.5%, so the gain is the choice and not the spending), **compare only byte-identical builds** (our first "redistribution does not pay" conclusion rested on a 0.97% size difference and was wrong), and **check what the search was allowed to try** (the published imatrix has no entry for the output head, which is where two thirds of the gain turned out to be). The write-up is [qwen38_alis_mlx/docs/bit-allocation.md](https://github.com/avlp12/qwen38_alis_mlx/blob/main/docs/bit-allocation.md). The method, with the numbers that produced it, is [docs/ACCELERATOR_OFFLOAD.md](docs/ACCELERATOR_OFFLOAD.md); the campaign it came from is [qwen38_alis_mlx/docs/ane-hybrid.md](https://github.com/avlp12/qwen38_alis_mlx/blob/main/docs/ane-hybrid.md).

- **When gradients are unavailable, sensitivity is still measurable — quantize one tensor group, leave the rest in bf16, and read the KL.** This is the transferable half of graded bit allocation, and it exists because the usual signals failed: the model's GatedDeltaNet layers have no VJP, so every gradient and DWQ path died in `nan` or OOM, and the public activation-statistics route (imatrix) is structurally the wrong quantity — sensitivity is `E‖G_t · Δ_t x‖²`, imatrix supplies only the input factor, and **RMSNorm erases the absolute scale that factor is made of**. A raw `in_sum2`-weighted knapsack improved **its own objective by 60.7%** and made KL **16–37% worse** than plain uniform. The forward-only probe — 106 groups over 506 quantizable tensors, under an hour on a 27B — needs no proxy at all, and three rules govern reading it. **Isolated damages are strongly sub-additive**: ours summed to 0.18974 where the joint build measured **0.09052**, a 2.1× overstatement, so the ranking chooses and only the built model measures. **A byte-matched control decides whether the finding exists**: spending the identical budget on arbitrary mid-depth FFN tensors bought −1.2% where the chosen five bought −17.5%. And **a predicate that matches nothing completes successfully** — our first allocation map hit 9 of 506 tensors (its keys were full paths, the predicate saw module suffixes), produced a silently uniform build after an hour of AWQ, and was briefly read as evidence that promotion does not compose with AWQ; read the shipped weights back and assert the packed shapes. Applied across three tiers of one model the same recipe bought **−18.9% pooled KL at 6-bit, −8.7% at 4-bit, and −2.3% at t = −1.6 (not significant) at 8-bit** — **bit allocation stops being the dominant error term before you run out of bits**, and the top tier ships graded because it costs nothing (+0.04% size, −0.2% decode), not because it helps. One hygiene rule underwrites all of the above: **diff against the bytes you published, by hash, not by filename** — our first 6-bit reading ("English not significant, t = −1.4") had been taken against a local directory whose name matched a variant the model card mentioned but had never shipped; against the artifact on the Hub it is **t = −10.1**, and two of three tiers' size conclusions inverted with the correction. The method is [docs/BIT_ALLOCATION.md](docs/BIT_ALLOCATION.md), with per-group damages, allocation maps and every paired KL run in [examples/qwen3.8-27b/results](examples/qwen3.8-27b/results).

- **A converter can drop an entire modality silently, and the artifact cannot tell you.** mlx-lm's `qwen3_5` `sanitize` discards `model.visual.*` and `utils.save_config` pops `vision_config` — so a 27B **VL** model converts to a text-only one with no warning, *and the output is indistinguishable from a conversion of a text-only model*. This is not hypothetical: when I surveyed the public MLX builds of this model I found conversions shipping the preprocessor config while carrying no vision weights at all. **A correction rides with this lesson**: my first census counted only the `.visual.` key pattern and so reported *zero* vision tensors everywhere, which was wrong — a later census of 283 repos found mlx-vlm-family conversions preserving the tower under `vision_tower.*`, some published before mine. The lesson survives the correction and gains one: **a census is a measurement, and a key pattern is its instrument** — grep for every naming convention the ecosystem uses before claiming an absence.
- **Fix pass-through generally, in `save()` — not per model.** A model declares `passthrough_patterns` and tensors it does not consume are copied through **as original bytes**, so `convert` and `awq` share one gate and future architectures inherit it. Four parts are load-bearing: (a) skip already-written keys by **suffix-aware** comparison, because `sanitize` reparents heads (`mtp.x` → `language_model.mtp.x`) and an exact-name check duplicates them in the index; (b) **read the bytes back and verify before advertising them in the index**; (c) keep the sub-config (`vision_config`) **only when the weights actually survived** — advertising an absent tower and hiding a present one are both bugs, the config must follow the bytes; (d) carry the preprocessor config with the weights. Verified: 333/333 vision tensors byte-exact, text decode 37.39 vs 37.61 tok/s (noise).
- **Never use the presence of an optional head as a format discriminator.** `should_shift_norm_weights = has_mtp_weights or has_unsanitized_conv1d` reads "this is a raw HF checkpoint" — but an *already-converted* checkpoint that kept its MTP head satisfies it too and gets its norms shifted **twice** (γ 0.94 → 1.94). No crash, no warning; generation collapses (ko NLL 1.679 → **17.460**, worse than uniform over a 248k vocab). Worse, MTP-free builds measure fine, so the evidence reads as "the MTP-preserving build is broken" — the bug frames the feature that exposes it. Upstream had it from a 35B MoE ([#1197](https://github.com/ml-explore/mlx-lm/issues/1197) / [#1623](https://github.com/ml-explore/mlx-lm/pull/1623)); we reproduced on a dense 27B and filed [#1735](https://github.com/ml-explore/mlx-lm/pull/1735).
- **Make the harness fail loudly about which library it imported.** Ours had been silently importing the installed stock mlx-lm instead of the fork under test — the silent fallback *was* the incident, and every measurement predating the fix had to be re-run. Put the fork explicitly first and **hard-fail** if stock resolves.
- **Queue-batched benchmarks hide latency; decode-path kernels need a dependent chain.** They avoid the ≈250 µs per-call sync floor, which is why we used them — but a hand-written quantized-matmul kernel that beat MLX in the queue-batched bench ran the *model* at 0.56–0.82×. The chained bench (N=K=5120, M=7) named it: MLX 0.0765 → 0.0789 ms (**+3%**), ours 0.0680 → 0.1530 (**+125%**). Throughput won, latency lost. "1.52× in the microbench" and "0.74× in the model" were **both true**. The split-K rewrite (8 simdgroups over K, `x` loaded device→MMA, no staging) fixed the chain (0.153 → 0.0558 ms, **1.41×**) and flattened the model's verify curve: S=7 70.5 → 44.6 ms (1.58×), S=8 77.1 → 43.3 (1.78×). Crossover is **M=6 on the chained metric** — at M=4 the kernel is neutral (0.98–1.10×) and dispatching it there made MTP k=3 slower. (Same family as the unchained-benchmark trap in the Motif-3 set, one level up: there it manufactured a number, here it inverted a verdict.)
- **When speculative decoding underperforms, price the verify curve before blaming the algorithm.** The 27B forward is 3.65× off the roofline at 8 tokens but only 1.19× off at 128 — backwards, and not physical. Cause: MLX's 4-bit `quantized_matmul` does not amortize at small `M` (**5.28× of M=1 at M=7, 6.32× at M=16**, where bf16 is flat at 2.00× across M=2..16); same on MLX 0.31.2 and 0.32.0, filed as [mlx#4265](https://github.com/ml-explore/mlx/issues/4265). Speculative decoding lives exactly in that window. The hybrid model's linear-attention kernels were the obvious suspect and were **acquitted** — measured standalone they are flat in T (0.28–0.37 ms, T=1..64), the recurrent state being register-resident already amortizes them.
- **A published reference implementation is not necessarily the canonical inference path.** Our DSpark drafter port matched the PyTorch reference to cosine **1.00000000** / 1.1e-4 max abs — and lost at 0.73× end-to-end, because the `spec_generate` bundled in the repo is **DFlash's** loop and never calls DSpark's own `markov_head` (127.1M, 9.3% of the drafter) or `confidence_head`; the real path lives inside SGLang. Parity proved we had faithfully ported the wrong loop. Wiring the head took acceptance **2.23 → 3.31** and end-to-end 0.73× → 1.20× (and, after the three integration defects in the next bullets, to **, landing above the model card's own acceptance figure under matched conditions (4.48 vs 3.39) — though note that acceptance number later proved to be the wrong objective, and the end-to-end ordering it implied was retracted under the EOS-cut protocol. Grep the reference loop for the checkpoint's distinguishing tensors before trusting it. (The port-side twin of the Motif lesson that a *published reference can be the broken one*.)
- **Building a feature and not wiring it was this campaign's single largest loss.** `fast_qmm.enable()` had **zero call sites outside the file defining it** — the split-K kernel was live only inside the scripts that benchmarked it, so `generate`, the server and both speculative loops ran without it (S=8 verify **70.1 ms instead of 43.1**). Nothing failed, nothing warned; the numbers were just the old stack's, and a shipping verdict got reasoned out on top of them. `grep` for the call sites of anything you just built — zero hits outside its definition means it does not exist in production — then wire it at the **loading** boundary with a killswitch, not at each call site. Corollary: a side lever tuned against it can be welded to it (rounding the `lm_head` batch into the kernel window is **+5%** with the kernel on, **−2%** with it off).
- **An optimization with a shape window is a claim about the run-time distribution — histogram it.** The kernel wins at M ≤ 8; the speculative loop was running at **mean verify width 9.50, max 16**, i.e. mostly in the regime that costs 2–2.6× more (≤8: 54.6 ms · 9–12: 106.8 · 13+: 142.8). A one-line clamp into the window was worth **41.2 → 59.1 tok/s (+43%)**. Outside its window a "fast path" is not neutral, it is a regression.
- **An unaccounted overhead is usually an unmeasured item.** A ≈32 ms per-step residual was rationalized as "the drafter's structural overhead" and used to justify shipping the other method; itemized, it was the two bullets above, and the step budget closed at **49.9 ms predicted vs 49.0 measured**. Require a step budget that closes before publishing any verdict resting on the difference.
- **Winning the drafter metric is not winning — and this lesson's own example was wrong twice.** I first wrote it
  pointing at DSpark (acceptance 4.23, losing end-to-end to the in-weights MTP head), then **inverted the verdict**
  once two defects were fixed, then **retracted the inversion's numbers entirely**: the harness had not been stopping
  at end-of-sequence, so a math prompt's post-EOS self-copy inflated acceptance to 4.53 and carried the headline.
  Under the corrected protocol — four prompts, EOS-cut, long-form, medians of three — the gated in-weights path leads
  (1.40×) and the external block drafter trails (1.28×). Two rules fall out. **Acceptance is not the objective: mean
  tokens committed per forward pass is**, and a drafter can win the first while losing the second. And **any
  speculative benchmark that does not stop at EOS is measuring the model copying itself**, which is the easiest
  possible continuation and the one where acceptance is meaningless.
- **A single-prompt speculative-decoding benchmark badly overestimates, and the workload spread can exceed the levers.** The same MTP k=2 read **1.41×** on a code prompt alone, **1.32×** over three English/code prompts, and **1.10×** over three prompts including Korean. Report the multi-workload number *and say which prompts*: after all the fixes above, on **Korean alone both speculative paths are slower than plain decoding** (plain 37.6 · MTP 34.3 · DSpark 33.3, cause not yet decomposed — we turn speculation off for Korean).
- **KV-cache quantization on a hybrid is a long-context lever only.** With 48 linear-attention + 16 full-attention layers, **only 16 of 64 layers hold a KV cache at all**. At 16K on the 4-bit build, peak barely moves — **20.80 GB** (bf16 KV) → 20.30 (8-bit) → **20.03** (4-bit) — with **top-1 100% preserved on all three** and decode −3%. The cache itself goes 16.8 → 4.2 GB at the full 262K context, which is the only place the trade pays.

**Added 2026-08-17, from the same campaign's second half** (two-box tensor parallelism, a served
stack, and a head retrained against its own quantized activations). The full record is the
[handoff](examples/qwen3.8-27b/HANDOFF.md); these are the parts that generalize off the model.

- **A distributed-collective deadlock leaves residue that process teardown does not clear — and
  failures observed in that state are not evidence about your code.** I chased one deadlock through
  a plausible hypothesis and two attempted fixes before running the control that mattered: restoring
  the exact code that had worked an hour earlier, which **still failed**. Rebooting the second box
  made that same code pass on the first try, including the sampled arm that had never once completed.
  The hypothesis had been fitted to observations taken from a wedged machine. Rule: **a box that has
  deadlocked a collective is rebooted before the next experiment**, and anything measured in between
  is inadmissible. Without it, hours go into fixing a defect that does not exist.
- **Dispatch overhead is already hidden in a well-formed decode loop, so kernel fusion pays only
  where the host still synchronizes.** Priced against a plan built on a 3-5 µs launch cost, the
  effective cost measured 1.2 µs — `async_eval` double-buffering had been absorbing the gaps all
  along. Plain-loop fusion projected to +2.4-3.1% and was abandoned at the gate; the same fusion
  bought real time inside the speculative loop, which does synchronize. Other stacks reporting large
  fusion wins are usually reporting on host-synchronous loops. **Measure the gap you intend to close
  before designing the thing that closes it.**
- **A speculative loop's fixed cost is scheduling, not weight reads.** Sharding the remaining
  unsharded projections across two machines recovered +4.7% against a paper estimate of +21%; a
  decomposition microbench had already put the honest ceiling at the measured value. The draft chain
  is dominated by per-step scheduling and gate synchronization, which tensor parallelism cannot
  touch. **Decompose before you shard.**
- **Shrinking per-forward time amplifies speculation, so a lever that fails alone can pass in
  combination.** Plain tensor parallelism missed its 1.4× gate (1.37×, landing exactly on the
  pre-registered break-even arithmetic). The same configuration with speculation on top cleared
  1.8× with room (2.07×). Gate combinations, not just levers.
- **As distribution speeds a model up, the serving layer becomes the bottleneck.** Going through
  HTTP cost approximately nothing on one machine and 15% on two, because the step time fell to ~13 ms
  and the per-token cost of SSE framing and detokenization stopped being noise. **The overhead you
  ignored at one speed is a first-class cost at the next.**
- **An oracle's two arms must share weights before it can measure wiring.** A "wiring mismatch" alarm
  at 1.4e-1 relative error turned out to be comparing a bf16 donor head against the deployed
  quantized one. With matched weights the gap collapsed 25× to bf16 rounding. **When an oracle fires,
  first ask what else differs between its arms.**
- **A quantized model's auxiliary heads can be retrained against its own activations, cheaply.** The
  vendor's multi-token-prediction head was trained on bf16 hidden states and then deployed reading
  4-bit ones. On-policy self-distillation — the quantized model writes its own transcripts, its own
  t+2 distribution is the teacher, plus a chain-step loss — moved the operating point +6.1%, and
  **+16.1% on the non-English long-form case that had been the weakest**. The head is re-quantized
  before shipping, so what users download is what was measured. This generalizes to any auxiliary
  head shipped alongside quantized weights.
- **Activation-aware quantization's advantage is monotone in how much damage there is to undo.** At
  4-bit AWQ beat uniform on every corpus slice; at 6-bit the same recipe measured better but sat
  inside its own noise; at 8-bit only one language slice separated. **Adopt it where the gap is,
  and let a pre-registered gate refuse it where it is not** — I ran that gate at 6-bit and rejected
  the swap rather than shipping a difference I could not certify.
- **A quantization format's value is conditional on the hardware having a unit for it.** Exact
  full-vocab KL across ten builds put nvfp4 and mxfp4 *behind* affine int4 with AWQ at equal file
  size on Apple silicon, which has no FP4 matmul path — the format's reason to exist is absent, so
  it only pays the dequantization cost. The same comparison on hardware with native FP4 should
  invert. **Do not carry a format verdict across silicon.**
- **Two independently produced artifacts landing on identical numbers is a free cross-check, not a
  bug.** Community 4-bit and 8-bit builds matched my uniform builds to five decimals; direct
  comparison showed the weights were **byte-identical** — affine group-wise quantization is
  deterministic and both pipelines started from the same release. Suspicion was right; the
  conclusion was that the whole measurement chain had just been validated end to end.
- **Verification is cheap only if you exclude what the filesystem invents.** Full sha256 comparison
  of a 200k-file backup reported every item mismatched; the destination filesystem had created
  AppleDouble sidecars (`._*`). Excluding those on both sides made it exact. The same run then
  flagged three real mismatches — all live files being appended during the copy — which is the
  distinction the exclusion lets you see. **Filter metadata artifacts, then treat what remains as
  signal.**
- **Pinning a harness to "not the stock library" does not pin it to "not a stale copy".** My
  benchmarks hard-fail if they import the installed package instead of my fork — a rule bought by
  an earlier incident. On a second machine that rule passed while the harness silently imported an
  *old checkout of the fork* sitting at a path the auto-discovery tried first: same project, months
  behind, missing the API the benchmark called. Identify the build you need **by capability** — does
  it expose the symbol this run depends on — not by path or by name. A staleness check is a
  different check from a provenance check, and only one of them was in place.
- **A shape-windowed optimization is a claim about the runtime distribution, and a compiler
  release can move that distribution out from under it.** A fused-attention path I added for an
  unsupported head dimension was adopted on measurement (+3.2% at one prefill shape) and, one
  upstream release later, measured **12.5% slower** at the chunk size actually used — upstream had
  widened its own coverage and tuned the path mine competed with. It still won at a chunk size the
  stack does not use. Retired. The rule this leaves: **re-run the A/B that justified an adoption
  whenever the layer underneath it ships**, and treat the original verdict as scoped to that
  version. Check the patch is still engaged before believing either result — mine was, verified by
  patched and stock builds returning different values for identical input.
- **Renderers pair single tildes into strikethrough, and a struck-out number reads as a retracted
  one.** Range notation (`2.3~2.5 ... 1.9~2.2`) in ledger prose silently crossed out the values
  between each pair on GitHub and on model cards. En dashes for ranges, `≈` for approximations,
  backticks around any literal tilde.

## Absorbed from upstream, not yet validated here

Ideas worth stealing from [omlx's oQ pipeline](https://github.com/jundot/omlx/blob/main/docs/oQ_Quantization.md) (reviewed 2026-07-10). None of these carry our own measurements yet — treat as roadmap, not method:

- **Batched-expert GPTQ.** All routed experts in a layer receive the same input hidden states, so they share one Hessian — oQ runs GPTQ over the whole expert bank at once (they report ≈15× vs per-expert). Complementary to DWQ: GPTQ is a cheap local error-compensation pass (minutes, forward-only calibration) where DWQ is end-to-end distillation (hours). Likely first target: a mid-2-bpw-class student *before* DWQ, to see whether the passes stack. **Code-audit caveat (omlx `d42528a`): the shipped `oq.py` contains no GPTQ/Hessian implementation — its `enhanced=True` path is imatrix-weighted affine clipping ("oQe").** Verify upstream code, not the docs, before planning around "oQ+ GPTQ". Existence proof at our scale: the [NF3-hybrid](https://huggingface.co/madeby561/GLM-5.2-MXFP8-NVFP4-NF3-Hybrid) ran per-expert GPTQ (Hessians from ≈23k routed tokens/expert) across all 753B expert weights — the pass is tractable; only the MLX implementation is missing.
- **Activation-weighted affine scale fitting.** Fit per-group `scales`/`biases` by activation-weighted least squares instead of min-max — same checkpoint format, better values, stock loading. Same compatibility trick DWQ itself relies on.
- **Normalized layer sensitivity for bit allocation.** `MSE(float, quant) / mean(float²)` per layer — the normalization keeps late layers from looking artificially sensitive under residual accumulation. Our measured-not-heuristic promotion lesson (Hy3: the sensitive band was mid-stack, not early/late) says automate this rather than trust priors.
- **Expert-coverage tracking of the calibration set.** oQ tracks which experts the calibration data actually activates. We have never measured what fraction of a 128–256-expert bank our 145-sample mix reaches per layer — undersampled experts get weak distillation signal in DWQ too. The diagnostic now ships here as `alis_dwq/expert_traffic.py` (§0); measurements on our own mixes still pending.
- **Stock mlx-lm AWQ, cascaded.** [LEARNED_QUANTS.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LEARNED_QUANTS.md) ships an AWQ pass (activation-aware per-channel scaling + clipping, salient-channel-protecting — consistent with the anchor lesson) and documents cascading it with dynamic quant and DWQ. **Scoping correction (2026-07-15): the full AWQ → clip_quantize → DWQ chain is NOT zero code** — `mlx_lm awq` emits only the quantized model, and `clip_quantize` needs the AWQ-*scaled float* weights as `--source` (re-deriving codes from the raw bf16 would silently undo the AWQ scalings; dequantizing the AWQ output is a forbidden lattice source). What is zero-code: AWQ vs naive at matched uniform bits (measures what the scaling pass buys), and AWQ → DWQ (DWQ trains scales/biases in place, no source needed). The clip link needs a small float-export hook in the AWQ pass first. **Second blocker (measured 2026-07-15): `mlx_lm awq` raises `NotImplementedError` for `qwen3_5`** — the pass supports a fixed model list, so the cascade experiment also needs an architecture port (or a supported-architecture testbed) before any of it runs.
- **Single-box oversized-teacher dump via mmap streaming.** [pulsar](https://github.com/giannisanni/pulsar) proves 97%-on-disk MoE forwards are workable (743B on dual 16 GB GPUs). Our teacher dump is forward-only at batch 1, and prefill reuses experts across the whole sequence, so a 790 GB Q8 teacher on one 512 GB box ≈ one full-model scan per sample through MLX's lazy mmap + page cache — roughly half a day for 145 samples *if* macOS eviction behaves under the wired limit. Would retire the entire 2-box distributed-dump trap list (§2b). Unvalidated; probe with a small layer-range forward before committing a run.
- **Lossless bf16 archival, if you must keep a bf16 master.** [brianbell-x/weight-compression](https://github.com/brianbell-x/weight-compression) packs BF16 sign+exponent into a 4-bit table code — bit-exact, ≈30% smaller, verified on GLM-5.2 (1,403→980 GB). Irrelevant to our shipped quants (packed low-bit ints have no BF16 mass), and for a `clip_quantize --source` the validated Q8 dump is smaller (≈790 GB) and loads natively — this only wins when losslessness itself is the requirement.

Caveat on their headline numbers (2-bit MMLU 64% vs mlx-lm's 14%): the baseline is *uniform* mlx-lm quantization. A sensitivity-graded mixed-precision recipe already captures much of that gap; the marginal value here is the error-compensation and scale-fitting passes on top of a good recipe, and it needs to be measured as such.

## Floor notes: how low the MLX container goes (2026-07-10)

Research and probe notes from scoping a sub-2.56-bpw GLM-5.2 build. The build ran on 2026-07-11: experts 2-bit/gs128 → 215.8 GB dec / **2.3225 bpw measured**, raw wikitext 4.711, after DWQ (the 4.5-bpw teacher won the A/B) **4.036** — full numbers in the [E1 floor-spike case study](examples/glm-5.2-e1-floor-spike/README.md).

- **The MLX affine floor is 2-bit** (mlx 0.31.2 probe: supported bits `{2,3,4,5,6,8}`; `bits=1` raises). 2-bit/gs128 is the lowest effective rate: (128·2+32)/128 = **2.25 bpw**. Probed end-to-end at gs128 — `quantize`/`dequantize`/`quantized_matmul` *and* gradients w.r.t. `scales`/`biases` — so layerwise DWQ supports a mixed-group-size student out of the box.
- **Ternary ("BitNet-style") inside MLX is dominated in bytes — but no longer in method.** Three levels are a subset of the 2-bit affine grid at identical storage, so ternary only pays in a genuinely sub-2-bit container (GGUF `IQ1_*`/`TQ*`; mainline llama.cpp now also carries Bonsai's `Q2_0` g64), which MLX doesn't have — and [PrismML's own MLX packs](https://huggingface.co/collections/prism-ml/bonsai-27b) pay exactly this tax (8.49 GB vs 7.17 GB GGUF). Conversion-by-training ([BitNet Distillation](https://arxiv.org/abs/2510.13998)) is demonstrated at 0.6–4 B; pure-PTQ ternary literature topped out at 70 B dense with heavy cost ([TWLA](https://arxiv.org/abs/2606.13054): +44% wikitext at W1.58; [PTQTP](https://arxiv.org/abs/2509.16989) is ≈4 bpw effective despite the name). ***Counterexample (2026-07)***: [Bonsai 27B](https://github.com/PrismML-Eng/Bonsai-demo) claims post-training ternary at 1.71 bpw holding 94.6% of FP16 (and 1.125 bpw at 89.5%) on a dense 27B hybrid — method proprietary (Caltech/Hassibi — the Optimal Brain Surgeon author, so a curvature-compensation lineage is the prior), evidence benchmark-only with sampling-temp asymmetry, MoE-745B transfer unknown. Weights are Apache-2.0 and the source model is public, so the claim and the method class are both checkable: see [examples/bonsai-27b-audit](examples/bonsai-27b-audit/README.md).
- **The practical floor converges across stacks.** [Unsloth's GLM-5.2 dynamic "1-bit"](https://unsloth.ai/docs/models/glm-5.2) (UD-IQ1_S GGUF) ships at **223 GB ≈ 2.4 bpw effective** for the same 745 B model — the size class a sensitivity-graded MLX 2.56-bpw build already occupies — while the same team's R1-671B went to 131 GB (1.56 bpw). The floor is model-dependent; below that line the fight is quality-per-byte (recipe + error-compensation passes + DWQ), not container size. *Update 2026-07-14*: [antirez's ds4-recipe GGUF](https://huggingface.co/antirez/glm-5.2-gguf) ships GLM-5.2 at **197 GB (≈2.1 bpw effective)** — routed experts ≈2-bit (IQ-class up/gate + Q2_K down, imatrix-weighted), everything decision-making (attention, router, shared experts, embeddings) at Q8. The "nobody under ≈220 GB" line is stale. *Measured 2026-07-15*: the [head-to-head](examples/glm-5.2-ds4-vs-alis/README.md) ran — matched 512-window PPL, identical corpus bytes, identical tokenization (window counts equal per slice): **wikitext and ZH are statistical ties (<1 SE), E1r wins code by 4.1% (≈2.3 SE)** at near-identical size (196.6 vs 201.0 GiB). The codebook+imatrix and affine+clip+DWQ stacks land on the same quality shelf; the affine container's missing-codebook handicap is fully bought back by clip + DWQ.
- **Ship the traffic census with the quant.** pulsar-class streaming engines warm their expert cache from a popularity census measured on first run (`.gguf.warm` sidecar). `expert_traffic --save traffic.npz` produces a better one (per-language slices) as a build byproduct — attach it to HF releases so streaming users skip the census, and state the flat-routing caveat (top-64 = 39–57% on GLM-5.2, so hit-rate expectations should be sized accordingly).

## Experimental features & rollback (v0.1 baseline)

Three additions landed 2026-07-12, motivated by REAP / router-KD (0xSero GLM-5.2-504B). The experimental training transforms remain opt-in and default-off. The current launcher is intentionally **not byte-identical** to the old baseline around I/O: memory gates, target contracts, no-clobber publication, and run evidence are now default safety behavior. The historical implementation is preserved as branch [`backup/v0.1-pre-router-kd`](https://github.com/avlp12/alis-dwq/tree/backup/v0.1-pre-router-kd) (commit `27863a7`). Every experimental path announces itself with an `[EXPERIMENTAL]` banner on stderr, so any session/model log shows at a glance whether a build used it:

First on-device validation (2026-07-13, GLM-5.2 3-bit-expert student, 8-bit teacher, K=6): **router-KD is harmless but did not help** — same-teacher valid loss edged the baseline (0.1357 vs 0.1365) yet held-out wikitext lost by a hair (2.7820 vs 2.7774, well inside the CIs). The valid-vs-held-out inversion pattern strikes again; the baseline shipped. `--norms` and `--loop-probe` are validated in production use (see the E1 case study and the measured-reference note in §0).

The 2026-07-13 batch (LoRA compensators, CKA monitor, `code_entropy`, `gen_calib`) carries no on-device measurements yet — validate on held-out PPL/KL before putting any of it in a shipping recipe. The LoRA adapter save/load round-trip in particular must be verified against `mlx_lm.load(..., adapter_path=...)` on-device before trusting a long run to it, and the CKA monitor exists precisely because the inversion above keeps recurring — use them together.
